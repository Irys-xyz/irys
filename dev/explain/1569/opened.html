Intent & approach

Each data-path index write (add_full_data_path + add_data_path_hash_to_offset_index) used to be its own MDBX transaction, committed synchronously on the calling thread inside StorageModule::write_data_chunk. The PR moves that commit off the caller entirely: every StorageSubmodule now owns a dedicated background thread ("index drain", crates/domain/src/models/index_drain.rs:70) that pulls queued IndexOps off an mpsc channel, batches up to 64 ops (index_drain.rs:20), and commits them in one db.update_eyre transaction (index_drain.rs:262). Callers submit an op and block on a per-op mpsc ack channel instead of taking the MDBX write lock themselves.

This forced a second change: write_data_chunk is split into prepare_data_index_writes (claims offsets, submits index ops) and finish_data_index_writes (waits for acks, then writes the packed bytes into pending_writes) — storage_module.rs:1813, storage_module.rs:1925. A new async sibling, write_data_chunk_queued (storage_module.rs:1790), moves the ack-wait onto tokio::task::spawn_blocking so the ingress hot path (chunk_ingress_service) does not recv() on a Tokio worker. A per-offset occupancy: HashSet<PartitionChunkOffset> (storage_module.rs:150) under the same lock as pending_writes now marks an offset as "claimed" for the window between submitting the index op and receiving its data.

Road not taken: the PR keeps one MDBX env and one dedicated OS thread per submodule (default 3 submodules per storage module, crates/config/src/submodules.rs:16) rather than a single node-wide batching writer or an async write-behind queue. That keeps each submodule's commit ordering local and simple, but it means batching — and the failure/atomicity boundary described below — is scoped per submodule, not per logical chunk write, which matters once a chunk's placements span submodules (see review-focus #1).

Delta semantics

Removed-behavior audit. The PR restructures write ordering enough to change two invariants and add a third; the table below lists old vs. new enforcement site for each.

InvariantOld enforcementNew enforcement
A pending ChunkType::Data entry only exists for an offset whose data-path index row is already durably committed. Neither branch of the old write_data_chunk guaranteed this: the pending-entropy path called pending.insert(.., ChunkType::Data) before add_data_path_to_index, and the disk-entropy path called write_chunk before the index add — a failed index commit left pending_writes at Data with no matching index row. Re-established — finish_data_index_writes only calls write_chunk after every prepared offset's index ack is Ok (storage_module.rs:1936), verified by failed_index_commit_does_not_insert_pending_data (storage_module.rs:1467).
recent_valid_chunks remembers a chunk hash only once it was actually accepted into storage. Chunk-ingress inserted the hash unconditionally right after the body-cache commit, before the storage-module write loop ran at all — a later critical SM-write error still left the hash cached, which per the code's own comment about retries "no-op at recent_valid_chunks" would silently swallow a legitimate retry. Re-established — remember_after_module_writes only inserts after write_chunk_to_assigned_modules returns Ok (chunks.rs:164), verified by failed_sm_write_does_not_remember_chunk_for_retry (chunks.rs:152).
An offset mid entropy→data conversion cannot be claimed by a second concurrent writer. None — no occupancy tracking existed; the only guard was the pending-writes lock's per-call granularity. New capability, not a re-establishment — occupancy set gates get_writeable_offsets (storage_module.rs:1752) and is claimed/released around each prepare/finish cycle.
A single write_data_chunk call is all-or-nothing across every offset it targets. True only incidentally — the old code processed offsets in one sequential loop inside one function, so a mid-loop error left only the offsets already visited in a (different) inconsistent state. Unaccounted for — finish_data_index_writes discards every prepared write, including ones whose index commit already durably succeeded in a sibling submodule, the instant any one offset's ack is an Err (storage_module.rs:1930). No test constructs a multi-submodule StorageModuleInfo to exercise this.

Ordering / concurrency. Index commits move from "on the caller's thread, inline with the rest of the write" to "on a per-submodule background thread, batched with other concurrent callers." That widens the set of things a single slow or failing write can be entangled with: a write_data_chunk_queued caller's latency now depends on whichever other ops land in the same ≤64-op batch (index_drain.rs:213).

Compatibility. StorageModule::add_data_path_to_index (the old public per-offset index-write method) is deleted outright rather than deprecated; a repo-wide search found no callers outside this file, so this is a safe removal, not a compatibility break.

Cross-file impact

  • crates/actors/src/data_sync_service.rs:60 and crates/actors/src/chunk_migration_service.rs:584 still call the synchronous write_data_chunk, invoked directly inside async fns on the shared Tokio runtime (data_sync_service.rs:738) without spawn_blocking. Blocking a Tokio worker here is not new (the old code also ran an inline MDBX commit on that thread), but the wait is now coupled to whatever else is in the same submodule's batch — including write_data_chunk_queued traffic from chunk ingress — which was not previously possible.
  • get_writeable_offsets (storage_module.rs:1752) and is_data_write_pending_at (storage_module.rs:684) were extended to consult occupancy. Every existing caller (chunk ingress's write_chunk_to_assigned_modules, the data-sync write path) transparently gets the new "occupied offsets are not writeable" filtering with no call-site changes — the previously-possible double-claim race on those offsets is now suppressed instead of surfaced.
  • chunks.rs:612 clones the Arc<StorageModule> list and drops the storage_modules_guard read lock before awaiting write_chunk_to_assigned_modules — required now that the write path crosses an .await point; holding a sync RwLockReadGuard there would previously have been a compile error or a held-lock-across-await hazard. Correctly handled.
  • Drop for StorageModule (storage_module.rs:2546) now shuts down every submodule's IndexDrain (joining its thread) before force_sync_pending_chunks runs. Since a writer thread can only be mid-write while holding its own Arc<StorageModule> clone, and Drop only fires once the last clone is gone, this does not race with an in-flight caller — no issue found here.

Review-focus map

These are attention pointers from reading the code, not verified findings. Recommend a dedicated code-review pass on #1 and #2 before merge.

1

storage_module.rs:1925 — cross-submodule partial-batch failure discards a durably-committed index row

Failure scenario: a chunk's data_root has two placements inside one StorageModule that land in different submodules (the default node config uses 3 submodules per storage module, submodules.rs:16, so this is the normal shape, not an edge case). prepare_data_index_writes submits one IndexOp per offset to each offset's own submodule drain. Submodule A's batch commits successfully; submodule B's fails (I/O error, or the test-only fail_next_index_commit hook). finish_data_index_writes (storage_module.rs:1930) sees the one Err and releases occupancy for every prepared offset without calling write_chunk for any of them — including submodule A's offset, whose add_full_data_path / add_data_path_hash_to_offset_index row is already durably committed (index_drain.rs:514). Until a retry resubmits the same chunk, submodule A's on-disk index claims a data-path exists at that offset while the chunk buffer there is untouched (still whatever it held before). All fixtures in this PR's tests use a single submodule spanning the whole offset range (e.g. storage_module.rs:1344), so this interaction is untested.

2

storage_module.rs:895 (reset) vs. index_drain.rs:213 (commit_batch) — ack delivery is not synchronized with wait_idle

Failure scenario: reset() bumps index_write_generation then calls wait_idle(), which unblocks as soon as clear_in_flight runs (index_drain.rs:250). But in commit_batch, clear_in_flight runs before send_ack (index_drain.rs:231-237) — so a writer whose op was already inside an in-progress batch at the moment reset() started waiting can still be sitting on done_rx.recv() after reset() has already cleared pending_writes and erased the submodule database (storage_module.rs:919). That writer then receives its Ok ack and calls write_chunk (storage_module.rs:1937), reinserting a ChunkType::Data entry into the just-cleared pending_writes map for an offset whose interval reset() just set to Uninitialized. The generation check only protects ops not yet pulled into a batch at bump time; it does not cover ops already past that check and mid-commit.

3

index_drain.rs:70 — one dedicated OS thread per submodule

IndexDrain::spawn starts a long-lived named thread per StorageSubmodule. With the documented default of 3 submodules per storage module (submodules.rs:16), a node with many assigned partitions materializes 3× that many index-drain threads for the life of the process. Not a correctness bug, but worth checking against the largest partition counts this is expected to run on.

Open questions

  • Was moving recent_valid_chunks's insert from "unconditional, before the SM write loop" to "only after write_chunk_to_assigned_modules succeeds" (chunks.rs:164) an intentional retry-safety fix bundled into this perf PR, or an incidental side effect of restructuring for .instrument().await? The PR description only mentions batching MDBX commits.
  • For review-focus #1: is the cross-submodule partial-failure window considered acceptable because a caller always retries the whole chunk until every offset round-trips cleanly? If so, is that retry guaranteed at every call site (chunk_ingress, data_sync_service, chunk_migration_service), or can a bounded-retry path give up while a submodule index still references a not-yet-written offset?
  • For review-focus #2: should IndexDrain::wait_idle block until acks are actually delivered to callers (not just until clear_in_flight runs), to close the reset() race?
  • Was the thread-per-submodule design validated against the largest expected submodules-per-node count in production, or is this expected to stay at the current default of 3 per storage module?
