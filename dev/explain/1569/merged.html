What it does & Why

Before this PR, every chunk write to a storage-module submodule triggered its own synchronous MDBX write transaction just to record the chunk's data-path index entry (crates/domain/src/models/storage_module.rs:1816). This PR moves that commit off the caller's path and into a dedicated background thread per submodule (crates/domain/src/models/index_drain.rs) that opportunistically batches up to 64 concurrent index writes into a single MDBX commit, and callers now enqueue an op and wait for an acknowledgement instead of committing inline. Alongside the batching, it hardens the write path: a second writer can no longer race an offset whose index write is already in flight, a failed storage-module write no longer marks the chunk as processed for retry purposes, and pausing/resetting a module now cancels in-flight index ops instead of letting them land afterward.

Why: stated reduce MDBX commit overhead under concurrent chunk ingestion — the PR description states: "Before: Each data-path index write was its own MDBX commit... After: Concurrent writes on one submodule share one txn (max 64)." The commit history (fix(storage): reject stale and in-flight index finalisation, three fix: address review findings commits) shows the batching change surfaced several correctness gaps around retries and pause/reset that got fixed in the same PR.

Change map

  • New per-submodule batching thread crates/domain/src/models/index_drain.rs Adds IndexDrain, a dedicated OS thread per submodule that receives IndexOps over an mpsc channel, drains up to crates/domain/src/models/index_drain.rs:20 (MAX_BATCH_SIZE = 64) ops per iteration, and commits them in one write_batch (crates/domain/src/models/index_drain.rs:269). A generation counter lets stale ops (queued before a pause/reset) be rejected without touching the DB (crates/domain/src/models/index_drain.rs:213).
  • StorageModule write path split into prepare / submit / await-ack / finish crates/domain/src/models/storage_module.rs:1855 write_data_chunk now delegates to prepare_data_index_writes, which reserves an "occupancy" entry per offset in PendingWrites (crates/domain/src/models/storage_module.rs:1855), submits an IndexOp per placement, then finish_data_index_writes (crates/domain/src/models/storage_module.rs:1994) inserts the packed chunk bytes into pending_writes only after every ack succeeds. A second writer targeting an already-occupied offset is now rejected instead of racing.
  • Async wrapper for tokio callers crates/domain/src/models/storage_module.rs:1824, crates/actors/src/chunk_ingress_service/chunks.rs:125, crates/actors/src/data_sync_service.rs:55 New write_data_chunk_queued waits for the drain's ack on tokio::task::spawn_blocking so the tokio runtime worker never blocks on an mpsc::Receiver::recv(). Chunk-ingress and data-sync switch to this async entry point; the body-migration worker keeps calling the synchronous write_data_chunk because it already runs inside its own spawn_blocking (crates/actors/src/chunk_migration_service/body_worker.rs:276).
  • Retry-safety fix: don't remember a chunk until the write succeeds crates/actors/src/chunk_ingress_service/chunks.rs:187 recent_valid_chunks (the LRU that suppresses re-processing of already-handled chunks) is now populated by remember_after_module_writes only after write_chunk_to_assigned_modules returns Ok (crates/actors/src/chunk_ingress_service/chunks.rs:638), instead of being populated unconditionally before the storage-module write was even attempted.
  • Pause/reset now cancel in-flight index ops crates/domain/src/models/storage_module.rs:726, crates/domain/src/models/storage_module.rs:916 pause_data_writes bumps index_write_generation so any op the drain later commits for a stale generation gets NACKed with WritesPaused. reset goes further: it bumps the generation, then calls index_drain.wait_idle() on every submodule before clearing pending_writes and wiping the submodule DB, closing a race where reset could run concurrently with an in-flight commit.

Behavior changes

  • Chunk marked as "seen" for retry purposes before as soon as prior validation passed, regardless of whether the storage-module write later failed → only after all assigned storage-module writes for that chunk succeed (chunks.rs:187). A failed write is now retryable instead of silently no-op'ing at recent_valid_chunks.
  • Data-path index commit granularity before one MDBX write transaction per chunk write, per submodule → up to 64 concurrently-queued chunk writes on the same submodule share one MDBX transaction (index_drain.rs:20). Only visible as reduced I/O and, per the "Watch out for" section, a wider blast radius per failed commit.
  • Second writer targeting an offset whose index write is already in flight before proceeded based on the generic pending-writes check, with no explicit in-flight concept → rejected outright with an explicit "index write already in flight" error (storage_module.rs:1987, surfaced via get_writeable_offsets/has_in_flight_index_for).
  • Chunk-ingress and data-sync calls into a storage module before committed the index write inline on the calling tokio task → await an ack from the submodule's drain thread via write_data_chunk_queued (storage_module.rs:1824). Not visible to end users; adds a hop that can add latency under drain contention (see "Watch out for").

Watch out for

  1. storage_module.rs:2032 — insert_pending_data_if_generation_current re-checks index_write_generation after the drain thread's MDBX commit already succeeded. pause_data_writes (storage_module.rs:726) only bumps the generation counter — it does not call wait_idle or touch the submodule DB the way reset does. So if a pause lands between the drain thread deciding to commit a batch and this function running, the data-path index entry is left durably committed in MDBX while the corresponding chunk bytes are never inserted into pending_writes (the function returns false → mapped to WritesPaused): an index entry could point at an offset whose chunk body was never queued for flush. worth a dedicated code-review pass
  2. index_drain.rs:213 — commit_batch maps a single failing MDBX commit to a failure for every op that happened to be opportunistically batched together (up to 64, via try_recv draining). Under concurrent load, one transient DB error now fails a burst of unrelated chunk writes simultaneously instead of just the one chunk that triggered it previously.
  3. chunks.rs:125 — write_chunk_to_assigned_modules awaits each assigned storage module in sequence. A chunk assigned to multiple modules now serializes behind however long each module's drain takes to flush its current batch, where previously each module's commit was independent and synchronous per module.
