Intent & approach

Every place the node reads an HTTP response body from another peer — the API client (IrysApiClient) and the gossip client (GossipClient) — previously called response.text() / response.json() directly, which buffer the entire body in memory regardless of size. The PR replaces every such call site with a shared streaming reader, read_capped_bytes, duplicated verbatim in both clients (crates/api-client/src/lib.rs:145, crates/p2p/src/gossip_client.rs:313), which enforces a new configurable ceiling max_peer_response_bytes (default 32 MiB, crates/types/src/config/node.rs:906).

The mechanism has two layers: a fast-path rejection on a declared Content-Length header that already exceeds the cap (no bytes read), and a streaming accumulator that reads via response.chunk() and calls the pure helper accumulate_response_bytes (crates/types/src/peer_response.rs:11) after every chunk, aborting as soon as the running total crosses the cap rather than waiting for EOF. This defeats both a lying Content-Length and an unbounded chunked-encoding body, and it aborts mid-stream instead of after a full buffer — the tests assert this explicitly by withholding the terminating chunk and checking the call still returns quickly (crates/api-client/src/lib.rs:152-179 in cap_tests).

The cap is plumbed as a required constructor argument on both clients rather than a global/thread-local default, so every call site that builds an IrysApiClient or GossipClient had to be updated to pass config.node_config.max_peer_response_bytes or the new DEFAULT_MAX_PEER_RESPONSE_BYTES constant — this is why the diff touches nine call sites across chain, chain-tests, and p2p test fixtures that have nothing to do with the capping logic itself.

Road not taken A global/static cap (e.g. a OnceLock or a constant) would have avoided touching nine constructor call sites, but would have made the cap unconfigurable per-node and untestable per-call (the new tests rely on constructing a client with an artificially tiny cap, e.g. IrysApiClient::new(8)). The threaded-parameter approach is more invasive but keeps the cap a first-class, validated config field.

New invariants

  • Bounded memory per peer response. No single call into IrysApiClient or GossipClient can buffer more than max_peer_response_bytes for one response, enforced uniformly (declared-length fast path + streaming fallback) rather than relying on the wire declaring the truth.
  • Config-level validation. Config::validate now rejects max_peer_response_bytes == 0 (crates/types/src/config/mod.rs:89) — a state-machine-adjacent guarantee: a running node can never reach a config state where every peer response is unconditionally rejected.
  • Overflow and over-cap are unified. accumulate_response_bytes treats u64 addition overflow the same as exceeding the cap (crates/types/src/peer_response.rs:16), so a cap near u64::MAX cannot be bypassed by wraparound — proven by property test (crates/types/src/peer_response.rs:46).

Error-contract changes

GossipClientError::GetJsonResponsePayload's second field was already String; call sites that previously did e.to_string() on a reqwest::Error now pass the String produced by read_capped_bytes/serde_json directly (e.g. crates/p2p/src/gossip_client.rs:623). No type-level change in the public error enum, but the message text for over-cap failures is new: "...exceeds cap of N bytes" instead of a reqwest network-error string, which anything doing string-matching on error messages (logs, tests) needs to tolerate.

Compatibility: a node upgraded to this PR that talks to an old peer sending a legitimately large body (> 32 MiB) will now hard-fail requests that previously succeeded. There is no protocol-version negotiation of the cap — it's a purely local, silent behavior change from the wire's perspective.

Review-focus map

1 · Design pressure — duplicated capping logic read_capped_bytes is implemented twice, near-verbatim, in crates/api-client/src/lib.rs:145 and crates/p2p/src/gossip_client.rs:313. Both crates already share accumulate_response_bytes from irys_types, so the streaming-loop wrapper around it (content-length pre-check, chunk loop, error formatting) is the only part not shared.
Failure scenario: a future fix to the streaming loop (e.g. handling a reqwest edge case in .chunk()) gets applied to one copy and not the other, silently reintroducing the unbounded-read bug in whichever client is missed.
2 · Non-2xx diagnostics are discarded when the error body itself is oversized crates/api-client/src/lib.rs:217-226 and the gossip equivalents replace the real error body with a generic cap message whenever a non-success response also happens to exceed the cap.
Failure scenario: a peer returns a 500 with a large but legitimate diagnostic payload (e.g. a verbose stack trace or validation report) that a misbehaving/misconfigured peer emits past 32 MiB — the caller now sees only "exceeds cap of N bytes" instead of the actionable error text, making the real failure harder to diagnose in logs. Low likelihood in practice (error bodies are rarely that large) but worth confirming this is the intended trade-off rather than an oversight of the "keep the diagnostic" test's scope, which only exercises small over-cap bodies (9 bytes vs. an 8-byte cap).
3 · Single global cap for structurally different endpoints The same 32 MiB ceiling applies uniformly to small JSON responses (handshake, peer list) and to inherently larger ones like get_block_index (crates/p2p/src/gossip_client.rs:869), whose response size scales with the caller-supplied BlockIndexQuery.limit (crates/types/src/block.rs:1163).
Failure scenario: if params.block_batch_size in the chain-sync path is ever raised well beyond current defaults, block-index sync could start failing against the new cap in a way that has nothing to do with a hostile peer — worth a sanity check on today's block_batch_size against the 32 MiB ceiling, though at today's default batch sizes each item (~tens of bytes) is nowhere close.

These are attention pointers based on reading the diff and its surrounding code, not verified bugs — a dedicated code-review pass (/code-review) would be the right next step to confirm #1 and #2 before merge, and to check current sync batch sizes against #3.

Open questions

  • Is discarding the real error-body diagnostic on an over-cap non-2xx response (review-focus #2) the intended behavior, or should the capped prefix of the body be surfaced instead of a generic message?
  • Was the duplication between the two read_capped_bytes implementations (review-focus #1) a deliberate choice to keep irys-api-client and irys-p2p decoupled, or would a shared helper (e.g. on a small trait, or a free function taking a reqwest::Response and a cap) be welcome as a follow-up?
  • Is 32 MiB sized specifically against today's largest legitimate payload (the PR's own comment ties it to "twice a 30M-gas execution payload" once hex-encoded, crates/types/src/config/node.rs:901), and is there a plan to raise it in lockstep if the gas limit changes, or is that left to operators via config?
  • Should the cap be negotiated or advertised between peers (e.g. in the handshake) so an old peer sending a body that used to be valid gets a clearer signal than a generic HTTP-layer failure, or is a hard local cutoff the intended permanent behavior?
