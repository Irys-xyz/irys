What it does & Why

What it does: ConsensusConfig::testing() now enables the Cascade hardfork from genesis — crates/types/src/config/consensus.rs:981 sets activation_timestamp: 0, 365/30-day term epoch lengths, and the live annual_cost_per_gb ($0.028/GB/yr), instead of cascade: None. Every test that relied on the old pre-Cascade default (two-ledger layout, allocation-age expiry, base $0.01 pricing) is updated to either opt back out with cascade = None or to assert the new Cascade-era numbers/behavior.

Why: stated intent — the PR description opens with "Cascade is live," i.e. the hardfork has already activated on a real network, so the testing default should match live behavior rather than a stale pre-activation snapshot. Before this change, a testing node "refused term-ledger price quotes and txs" for the OneYear/ThirtyDay ledgers.

  • Any test or tool built on ConsensusConfig::testing() without overriding hardforks.cascade now starts with term ledgers (OneYear, ThirtyDay) present and the Cascade annual_cost_per_gb ($0.028/GB/yr) in effect, rather than the base rate ($0.01/GB/yr) → term-ledger price quotes and transactions that previously failed with "ThirtyDay ledger not available: Cascade hardfork not active" now succeed by default.
  • The keccak256 hash of the testing consensus config changes (65At1Z… → 26uQbM…), since the hardforks section is part of the hashed config (crates/types/src/config/consensus.rs:1449).
  • Storage-fee amounts computed from the default testing config are ~2.8× larger than before, since fees are linear in annual_cost_per_gb and the Cascade rate ($0.028) replaces the base rate ($0.01) whenever Cascade is active at the quoted timestamp.

Watch out for

crates/types/src/config/consensus.rs:1449 — the testing consensus-config hash changed; any downstream tooling, snapshot, or fixture outside this repo that pins the old hash (65At1ZvKVtUPtR1jLtA8CcFYX2vHf7tT5TbhBEy3u2XE) will now mismatch and needs updating.
crates/chain-tests/src/validation/cascade_term_expiry.rs and the other files pinned to cascade = None — the PR description itself flags this: the pre-Cascade allocation-age expiry tests were pinned to the old behavior rather than rewritten for Cascade's write-anchored expiry rule. Cascade-era equivalents exist (cascade_term_expiry, cascade_submit_expiry_promotion, perm_partial_frontier_survives_cascade), but the allocation-age code path itself is now only exercised via the non-default, opted-out configuration — worth a dedicated code-review pass if that coverage gap matters for release sign-off.
crates/chain-tests/src/validation/poa_cases.rs:149 — the partition-assignment lookup added a ledger_id == Submit filter because slot indices now repeat across ledgers (Publish/OneYear/ThirtyDay/Submit). Any future test that adds a bare .find(|pa| pa.slot_index == Some(n)) without a ledger filter against the default testing config will silently match the wrong ledger's slot.
crates/types/src/storage_pricing.rs:1750 — the untouched spreadsheet-golden tests further down this file (~L1736-2400) set the base config.annual_cost_per_gb field directly and call the non-timestamp-aware cost_per_chunk_per_epoch(), bypassing the Cascade override entirely even though Cascade is now active by default on the config they build from ConsensusConfig::testing(). They still pass because they never route through effective_annual_cost_per_gb, but a future edit that switches them to the Cascade-aware path would need to account for the now-active $0.028 override.
crates/chain-tests/src/validation/ledger_expiry_with_unstake.rs:110 — the fix relies on Cascade's expiry clock starting at the epoch block that records the write, one epoch later than before; per the author's own test notes, irys-multiversion-tests was not run for this PR, so cross-version behavior around this same timing change is unverified (though that crate doesn't reference cascade or ConsensusConfig::testing() directly, so the exposure looks limited).
