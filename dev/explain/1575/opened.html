Intent & approach

crates/types/src/config/consensus.rs:967 contains the block that builds ConsensusConfig::testing(). This PR flips one field in it: hardforks.cascade goes from None to Some(Cascade { activation_timestamp: 0, one_year_epoch_length: 365, thirty_day_epoch_length: 30, annual_cost_per_gb: default() }) (crates/types/src/config/consensus.rs:980-988). Every other file in the diff is downstream fallout from that one flip: golden values, ledger counts, submodule provisioning, and epoch timing that were implicitly relying on the old default.

The stated intent (PR description, commit message) is that Cascade is live on the real network, so the testing config should model the live rule set by default — tests that specifically want pre-Cascade behavior should say so explicitly via cascade = None, rather than the reverse (pre-Cascade being free and Cascade tests opting in). This is a pure default-flip strategy: no production code changes, no new capability, no hardfork-gating logic touched. The road not taken is a parallel ConsensusConfig::testing_pre_cascade() (or similar) that pre-Cascade tests could opt into instead of scattering cascade = None across ~19 call sites; the PR author chose per-test opt-out over a second named config, presumably because most of the pre-Cascade tests are exercising something Cascade-specific about that scenario (allocation-anchored expiry, a fixed two-ledger partition layout) and want that fact visible at the call site, not hidden in a helper's name.

The PR is entirely test/config-default code — no file under a non-test, non-config path changes production logic. The only behavior a production binary sees differently is a config file: the TOML round-trip test at crates/types/src/config/mod.rs:1210-1215 gains a [hardforks.cascade] section, confirming the serialized shape, not a new field.

Delta semantics

The core contract change: ConsensusConfig::testing() now returns a 4-ledger config (Publish, Submit, OneYear, ThirtyDay) with live Cascade fee rates, instead of a 2-ledger config (Publish, Submit) at the base fee rate. Every test that constructs a node/config via NodeConfig::testing() / ConsensusConfig::testing() and does not override hardforks.cascade is now exercising the Cascade code path where it previously exercised the pre-Cascade path. Two contracts move as a direct result:

  • Ledger set. Ledgers::new derives its ledger count from whether Cascade is active (crates/database/src/data_ledger.rs:934-944: ledgers.len() == 4 when Cascade is active vs. 2 when inactive). Testing nodes now allocate genesis partitions across 4 ledgers instead of 2.
  • Fee rate. cost_per_chunk_per_epoch_at reads effective_annual_cost_per_gb, which returns the Cascade override ($0.028/GB/yr) instead of the base rate ($0.01/GB/yr) whenever Cascade is active at the given timestamp (crates/types/src/config/consensus.rs:611-629). Every fee computed through this timestamp-aware path in a default testing config is now 2.8x its old value. Note the non-timestamp-aware sibling, cost_per_chunk_per_epoch() (consensus.rs:601-607), still reads the base annual_cost_per_gb unconditionally and is untouched by this default — the two pricing-endpoint tests had to be switched from the non-aware to the _at variant to keep testing what the real API path does.
  • Expiry anchor. Not changed by this PR, but its effect surfaces throughout: pre-Cascade Submit-slot expiry is allocation-anchored (age since the slot was created); Cascade anchors expiry on the slot's last write, and only once the slot is fully written. This is why so many of the "set cascade = None" edits are paired with a comment naming which of the two rules the fixture depends on.

Cross-file impact

  • poa_cases.rs:148-154 — multi_slot_poa_test's partition-assignment lookup now filters by pa.ledger_id == Some(DataLedger::Submit.into()) in addition to slot_index. Before this PR, with only Publish and Submit active, a bare slot_index match happened to be unambiguous for this test's genesis signer. With OneYear and ThirtyDay now also present at genesis, both of those term ledgers get a slot 0, so an unfiltered .find() over get_partition_assignments could match a term ledger's partition instead of Submit's. The same file already used the ledger_id-qualified form elsewhere (poa_cases.rs:354), so this brings the one straggler in line rather than introducing a new pattern.
  • poa_cases.rs:41-42 and data_size.rs:37-38 — both call StorageSubmodulesConfig::load_for_test(..., 5) before packing starts, up from whatever the implicit default provisioned. This is necessary because crates/config/src/submodules.rs:153-161 auto-creates exactly 3 submodules when no config file exists yet — a constant untouched by this PR, sized for the old default of 2 ledgers with modest slot counts. With Cascade's 2 extra term ledgers now consuming genesis partitions from the same pool, these two tests (which each need multiple Submit slots on top of one partition per ledger) run out of capacity under the old default and needed an explicit bump. See the Review-focus map for why this fix looks locally scoped rather than systemic.
  • pricing_endpoint.rs:86-91 and pricing_endpoint.rs:205-210 — switched from cost_per_chunk_per_epoch() to cost_per_chunk_per_epoch_at(UnixTimestamp::from_secs(0)). Callers of the base (non-_at) method elsewhere in the codebase are unaffected by the new default — that method never consulted Cascade — but that also means any other test still calling the base method to model what the live pricing endpoint charges is now silently checking the wrong (pre-Cascade) number, since the endpoint itself is timestamp-aware.
  • ledger_expiry_with_unstake.rs:110-119 — heavy_test_ledger_expiry_uses_custom_reward_address now mines a third epoch before checking expiry, because Cascade starts the clock at the epoch that records the write (epoch 1) rather than at allocation (epoch 0). Any other still-passing test that asserts an expiry height by counting epochs from allocation, rather than from last write, is a candidate for the same off-by-one under the new default if it happens not to have been caught by this PR's test run — see Review-focus map.

Review-focus map

These are attention pointers from the analysis above, not verified findings. Recommend a dedicated code-review pass (/code-review) to confirm any that look serious before merging.

  1. 1 crates/config/src/submodules.rs:153-161 — the hard-coded default of 3 auto-created submodules is untouched by this PR, but the default testing config it serves jumped from 2 ledgers to 4. Failure scenario: any existing (or future) chain-test that calls IrysNodeTest::new_genesis(...) without an explicit StorageSubmodulesConfig::load_for_test call, and that needs a genesis partition in more than one ledger to reach the assertion it cares about (not just the two tests this PR patched), can now come up short on partitions in a way that manifests as an unrelated-looking failure deep in packing or slot assignment rather than as an obvious config error. The PR's own test-run notes (1739 + 1090 + 328 tests passing) suggest this is not widespread today, but the fix here was per-test rather than a change to the shared default, so the next test added against the new default inherits the same risk with no guardrail.
  2. 2 crates/chain-tests/src/validation/ledger_expiry_with_unstake.rs:110-119 — the fix (wait one more epoch) is a symptom of a codebase-wide semantic shift: any test that computes "data expires at allocation epoch + submit_ledger_epoch_length" is now off by however many epochs elapse between allocation and the write that Cascade anchors on. Failure scenario: a test with a similarly allocation-anchored expiry-height calculation that happens to allocate and write in the same epoch block would see no discrepancy (write epoch == allocation epoch), masking the bug for that specific timing but not for a fixture whose write lands even one epoch later — worth a search for other "epoch N: data expires" style assertions that weren't touched by this PR.
  3. 3 crates/chain-tests/src/api/pricing_endpoint.rs:86-91 (and its sibling at :205-210) — now the only two call sites of cost_per_chunk_per_epoch_at in the diff; every other consumer of the plain cost_per_chunk_per_epoch() outside this PR's changed files is unaffected by the new Cascade default and will keep quoting the base rate. Failure scenario: if any other test asserts what the live pricing HTTP endpoint charges by calling the non-timestamp-aware method (instead of following this PR's pattern), it now silently checks a number 2.8x too low relative to what the endpoint actually returns, and would only be caught by chance if its tolerance happens to be loose enough to still fail loudly.

Open questions

  • Was a second named config (e.g. ConsensusConfig::testing_pre_cascade()) considered instead of the ~19 inline cascade = None overrides? The current approach makes each pre-Cascade test's dependency explicit at the call site, but it also means the next contributor adding a pre-Cascade scenario has to remember the incantation rather than reach for a named constructor.
  • Should crates/config/src/submodules.rs's hard-coded default of 3 auto-created submodules (submodules.rs:153-161) be revisited now that the testing default provisions 4 ledgers rather than 2, or is per-test load_for_test the intended pattern going forward for any test that needs more than the bare minimum?
  • irys-multiversion-tests was not run for this PR (noted in the description). Does that suite construct consensus configs independently of ConsensusConfig::testing(), or does it inherit this default too and need the same audit before merge?
  • Is the flaky failure noted for multi_node::ema_forks::spiky_slow_heavy4_ema_intervals_roll_over_in_forks (one failure, three reruns passing, also intermittent on master) confirmed unrelated to the Cascade default change, or only presumed so because it reproduces on master too? Worth one more look if it recurs in CI.
