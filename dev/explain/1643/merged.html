What it does & why

GET /v1/price/{ledger}/{size} rounds the requested size up to a whole number of chunks before computing a fee quote. That round-up used an unchecked div_ceil(chunk_size) * chunk_size — for a size near u64::MAX the multiply overflows. The PR adds a bounds check: if the requested size's chunk count exceeds crates/api-server/src/routes/price.rs:60 consensus.mempool.max_data_tx_chunks (the same cap mempool ingress and consensus prevalidation already enforce on real transactions, from #1533), the route now returns 400 before the multiply ever runs.

Why — stated intent (PR description & commit message) The build profile mainnet runs (debug-release, and [profile.release] with overflow-checks = true) panics on integer overflow, and the panic hook aborts the whole node. An unauthenticated client exploited this by requesting a price quote for a size near u64::MAX, crash-looping mainnet nodes on 2026-10-18. This is a hotfix port of #1640 (already merged to mainnet) onto release/4.x.

Change map

  • Bound the chunk count before multiplying (crates/api-server/src/routes/price.rs) — compute chunks = max(chunk_size, bytes_to_store).div_ceil(chunk_size), reject with 400 if chunks > max_data_tx_chunks, and only then compute bytes_to_store = chunks * chunk_size. The overflow-prone multiply now only ever runs on an already-bounded chunks value. See crates/api-server/src/routes/price.rs:53-71.
  • Regression test for the crash and the new boundary (crates/chain-tests/src/api/pricing_endpoint.rs) — new test heavy_pricing_endpoint_rejects_size_over_max_tx_size asserts exactly-max-size succeeds (200), one byte over fails (400), u64::MAX fails (400) instead of crashing the process, and the node still answers a normal request afterward. See crates/chain-tests/src/api/pricing_endpoint.rs:183-215.

Behavior changes

  • Requests with chunk count > max_data_tx_chunks: previously the multiply chunks * chunk_size ran unconditionally and could overflow u64 for sizes near u64::MAX, which — under the overflow-checked build profile mainnet runs — panicked and aborted the node before: crash → now the route returns 400 Bad Request with a message naming the byte limit, and the node keeps serving other requests after: 400.
  • Requests with chunk count ≤ max_data_tx_chunks (including exactly at the max): unchanged — still rounds up to the next whole chunk and returns a 200 price quote, per the test's exactly-at-max-size assertion at crates/chain-tests/src/api/pricing_endpoint.rs:193-195.
  • Error message shape: new 400 responses for oversized requests now carry the text "Data size exceeds the maximum transaction size of {n} bytes", a response shape that did not exist on this route before (previously no request could reach this particular rejection path).

Watch out for

  • crates/api-server/src/routes/price.rs:65 — the error message computes max_chunks * chunk_size to report the byte limit; this is the same multiply shape that overflowed in the bug being fixed, just with max_chunks (a fixed, small, config-bounded value — 5 TiB / chunk_size on mainnet) instead of the unbounded user-supplied chunks. It cannot overflow with today's config values, but it is a non-overflow-checked multiply sitting one line below a fix for an overflow bug, so a future config change to max_data_tx_chunks or chunk_size is worth a mental note here.
  • crates/api-server/src/routes/price.rs:61 — the new check is placed after the DataLedger::try_from conversion but before the per-ledger match (Publish / Submit / term ledgers); a reviewer should confirm the Submit / term-ledger branches don't have their own, independent path to the same overflow (this diff only touches the single shared check before the match, so if another code path recomputed chunk counts separately it would not be covered — worth a dedicated code-review pass to confirm there is no such second path).
