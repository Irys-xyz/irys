Intent & approach

GET /v1/price/{ledger}/{size} computed bytes_to_store by rounding the path-supplied size up to a whole number of chunks via an unchecked div_ceil(chunk_size) * chunk_size. For size near u64::MAX the multiply overflows; because the node's release profile sets overflow-checks = true (Cargo.toml:400), that overflow panics, and the node's custom panic hook (crates/chain/src/main.rs:72) turns any panic into a process abort. An unauthenticated, single HTTP request was enough to crash-loop mainnet nodes (stated in the PR description, dated 2026-10-18).

The fix rejects the request with 400 before the multiply ever runs, whenever the requested chunk count exceeds consensus.mempool.max_data_tx_chunks (crates/api-server/src/routes/price.rs:60). This is the same cap already enforced at mempool ingress and consensus prevalidation via data_tx_structural_defect (crates/actors/src/data_tx_validation.rs:63), so the approach is semantic, not just mechanical: a quote is never returned for a size that could never become an accepted transaction, and bounding the chunk count before the multiply incidentally also bounds the multiply itself.

Road not taken: the overflow could have been fixed purely mechanically — swap the unchecked multiply for checked_mul or saturating_mul and return a generic error (or a clamped value) on overflow. That would have stopped the crash without encoding "this size can never be accepted" as a 400. The chosen approach instead reuses the mempool/consensus cap as the rejection boundary, which is more informative to callers (a real error message naming the max transaction size) but, as discussed in Review-focus map, introduces a third, independently-written site that encodes the same cap-comparison rule.

The commit message and PR description both state this is a cherry-pick of mainnet hotfix #1640 onto release/4.x, applied "cleanly" — i.e. no conflict resolution was needed, so the diff is expected to be the hotfix verbatim.

Delta semantics

API contract — error response: before this change, any size whose chunk count exceeded max_data_tx_chunks either (a) succeeded and returned a quote for a tx that mempool ingress/consensus would later reject anyway, or (b) for sizes close to u64::MAX, aborted the process. After this change, such sizes uniformly get a 400 with a message naming the byte-size cap, before any EMA lookup, block-tree read, or fee calculation runs (crates/api-server/src/routes/price.rs:61-70). The check sits above the match data_ledger (crates/api-server/src/routes/price.rs:73), so it applies uniformly to Publish, Submit, OneYear and ThirtyDay alike, even though Submit is rejected for an unrelated reason a few lines later.

Compatibility: purely additive from a valid-client point of view — every size that previously returned 200 with a correct quote still does (the test asserts the exact-max-size boundary stays 200: crates/chain-tests/src/api/pricing_endpoint.rs:55-57). Only requests that were already doomed to be rejected downstream (or that crashed the node) observe a behavior change, and they now get a normal HTTP error instead of a crash or a misleading quote.

Cross-file impact

get_price has no in-process Rust callers beyond its own route registration — it is wired up once, at crates/api-server/src/lib.rs:141 (.route("/price/{ledger}/{size}", web::get().to(price::get_price))). The more relevant "cross-file" relationship is semantic rather than call-graph: the new check at price.rs:61 duplicates the comparison already centralized in data_tx_structural_defect at crates/actors/src/data_tx_validation.rs:63, which that module's own doc comment says exists specifically "to keep the two gates from drifting" (crates/actors/src/data_tx_validation.rs:1-7). That helper takes a DataTransactionHeader, not a bare size, so it isn't directly callable from the quote endpoint without refactoring — the duplication is a reasonable consequence of the type mismatch, not obviously a mistake, but it is now a third site carrying the same arithmetic rule. Review-focus map attention pointers, not verified findings

  1. crates/api-server/src/routes/price.rs:65 — the rejection message computes max_chunks * chunk_size to report the byte cap. This multiply is unguarded, same shape as the bug this PR fixes, just operating on config values instead of request input. Config validation only enforces max_data_tx_chunks > 0 (crates/types/src/config/mod.rs:163-166) — there is no check that max_data_tx_chunks * chunk_size stays within u64. With today's mainnet value (20,971,520 chunks × a 256 KiB-class chunk_size) this is nowhere near overflowing, but a future config change that raises max_data_tx_chunks or chunk_size without re-deriving this bound would reintroduce the exact crash-loop class this PR exists to close — this time gated by config rather than by an attacker-supplied path parameter, so it would only surface once that config ships. Worth a dedicated code-review pass if max_data_tx_chunks or chunk_size are ever planned to change.
  2. crates/api-server/src/routes/price.rs:60-61 — the cap check is a hand-written comparison rather than a call into crates/actors/src/data_tx_validation.rs:40-70, the function that exists specifically so mempool ingress and consensus prevalidation can't drift apart on this rule. If that shared function's comparison ever changes (e.g. a stated-intent change to off-by-one semantics, or an added condition folded into "oversized"), this third site in price.rs won't pick it up automatically: a future edit to the mempool/consensus rule, state -> quote endpoint now disagrees with what mempool/consensus will actually accept, either quoting a price for a transaction that will be rejected on submission, or rejecting a quote request for a size that would actually be accepted.
  3. crates/chain-tests/src/api/pricing_endpoint.rs:184-213 — the new test covers the exact-max/max+1/u64::MAX boundary and a post-rejection liveness check, but exercises only DataLedger::Publish. The fix applies before the ledger match (price.rs:61), so Submit/OneYear/ThirtyDay get the same bound for free by construction — low risk — but the test suite doesn't assert that for those ledgers directly, so a future refactor that moves the check inside the match arm would not be caught by this test.
