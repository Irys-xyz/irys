Intent & approach

A crafted GET /v1/price/{ledger}/{size} request with size near u64::MAX panicked the node: the handler rounded the requested size up to a whole number of chunks via bytes_to_store.div_ceil(chunk_size) * chunk_size (crates/api-server/src/routes/price.rs:55), an unchecked multiply that overflows for large inputs. On mainnet's debug-release profile — which inherits [profile.release]'s overflow-checks = true (Cargo.toml:400, Cargo.toml:429) — the overflow triggers a panic, and the node's panic hook aborts the process rather than unwinding the single request. The PR description states this was observed as an unauthenticated client crash-looping mainnet nodes on 2026-10-18.

The chosen fix is a pre-condition check, not a narrower arithmetic fix: compute the chunk count first, reject with 400 if it exceeds consensus.mempool.max_data_tx_chunks (crates/api-server/src/routes/price.rs:60), and only then perform chunks * chunk_size (crates/api-server/src/routes/price.rs:71). The road not taken: switch the multiply to checked_mul/saturating_mul and return a generic "size too large" error without reference to the tx-size cap. The PR picks the cap-based rejection instead because it is semantically correct, not just panic-safe — a size whose chunk count exceeds max_data_tx_chunks could never be accepted as a real data transaction by mempool ingress or consensus prevalidation either, so quoting a price for it was already a correctness bug (a client could get a quote for a transaction that would then be rejected on submission), independent of the crash.

This is a cherry-picked port of mainnet hotfix #1640 onto release/testnet/4.x, stated as already hot-deployed to testnet peers 2–7 and 10 before this PR record was produced.

Delta semantics

API contract (new): GET /v1/price/{ledger}/{size} now returns 400 Bad Request with body {"error":"Data size exceeds the maximum transaction size of <N> bytes"} for any size whose div_ceil(chunk_size) chunk count exceeds max_data_tx_chunks (5 TiB-equivalent chunk count on mainnet/testnet config). Previously every size up to the point of overflow returned 200 with a computed quote; there was no upper bound tied to transaction-size policy.

Ordering: the cap check runs after ledger-type validation (crates/api-server/src/routes/price.rs:50-51) and before any canonical-chain/EMA lookups, so an oversized request now short-circuits before taking the block_tree read lock — a minor, incidental improvement (one less lock acquisition on the crash-loop path), not a stated goal.

Compatibility: no on-disk or wire format changes. Any existing client that was relying on getting a (meaningless, unsubmittable) quote for an over-cap size now gets a 400 instead — this is the intended behavior change, and matches what would happen if that client then tried to actually submit a transaction of that size.

Cross-file impact

The changed symbol is the HTTP handler get_price (crates/api-server/src/routes/price.rs:42), which has no in-repo Rust callers besides the Actix route table and tests — its only consumers are external HTTP clients, so there is no internal caller to audit for a mishandled new precondition.

The response shape is unchanged (PriceInfo JSON on 200); only the domain of accepted size values shrank, and the error path reuses the existing (String, StatusCode) -> ApiError conversion (crates/api-server/src/error.rs:94-98), so the error envelope ({"error": "..."}, correct status code) is consistent with every other rejection this handler already produces (e.g. the ledger-type check at price.rs:50-51). No caller needs updating for a changed return type or exception.

The max_data_tx_chunks cap this PR reads is the same consensus constant already enforced independently in three other places: mempool ingress and consensus prevalidation share one structural check, data_tx_structural_defect (crates/actors/src/data_tx_validation.rs:40-69), and block-production tx selection filters on it directly (crates/actors/src/tx_selector/mod.rs:506-542). This PR adds a fourth, independent inline reimplementation of "chunks > max_chunks" in the API layer rather than calling into the shared helper — see the design-pressure note under review-focus.

Review-focus map

  1. crates/api-server/src/routes/price.rs:65 low severity — the error-message format string computes max_chunks * chunk_size, an unchecked multiply of two config-derived values, structurally identical to the multiply this PR just removed for request-derived values. Failure scenario: if an operator ever configures mempool.max_data_tx_chunks large enough that max_chunks * chunk_size > u64::MAX (not possible with today's shipped configs — mainnet/testnet use ~20.97M chunks × 256 KiB ≈ 5.5 TiB, far below the limit — but nothing in crates/types/src/config/mod.rs:163-166 enforces an upper bound, only "> 0"), every oversized-size request would panic the node again, on the exact same overflow-checks-on/panic-hook-aborts path this PR exists to close. Low likelihood today because the input is operator config, not attacker-controlled, but it reintroduces the same bug shape inside the bug's own fix. Worth a dedicated code-review pass if config bounds aren't validated elsewhere.
  2. crates/api-server/src/routes/price.rs:60-70 design pressure — this is the fourth independent inline reimplementation of the "chunks > max_data_tx_chunks" check (alongside data_tx_validation.rs:63 and its two call sites). The module comment at data_tx_validation.rs:1-11 states the shared helper exists specifically "to keep the two gates from drifting." A future change to the comparison (e.g. an off-by-one, or switching to >=) made in data_tx_structural_defect would silently not apply to the price endpoint, and vice versa, since they are no longer the same code. This is a pattern/pressure observation, not a bug: the duplication is currently byte-identical in intent (chunks > max_chunks in both places) and the API-layer check operates on a raw size: u64 path parameter rather than a DataTransactionHeader, so reuse would need a signature-level refactor, not a copy-paste fix.
  3. crates/chain-tests/src/api/pricing_endpoint.rs:184-212 test coverage — the new test exercises exactly-at-cap (200), one-chunk-over (400), u64::MAX (400), and post-crash liveness, which is the right boundary set for the panic this PR fixes. It does not exercise a size that is non-zero but smaller than one chunk (the pre-existing max(chunk_size, bytes_to_store) floor), though that path is unchanged by this PR and is covered by the pre-existing heavy_pricing_endpoint_round_data_chunk_up test at pricing_endpoint.rs:215. No gap specific to this change.
