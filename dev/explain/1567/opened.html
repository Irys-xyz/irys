Intent & approach

The stated trigger: devnet n3 froze at block 29875 behind a 4.43 GiB Submit tx. ChunkMigrationService did index writes, chunk-body writes, and a per-tx fsync in one synchronous pass per block (crates/actors/src/chunk_migration_service.rs:280); one oversized tx's body copy blocked every subsequent block's index writes, so the Publish ledger's promotions (indexed via the same path) never landed and data sync parked the whole span on MissingDataRootIndex.

The fix separates two concerns that were previously fused into one synchronous call:

Index path — on_block_migrated

Runs inline, in block order, MDBX only.
tx_path / DataRootInfo → per-submodule txn
+ PendingBodyMigration{data_root, data_size, start_offset, block_height, attempts:0}
~40 bytes per tx, regardless of tx size.
→

Body path — body_worker.rs

Background, one spawn_blocking task per submodule with outstanding rows.
cache hit → write_data_chunk
cache miss (Publish only) → durable Submit replica
no source → left for data sync
512 writes/pass budget; stops at a pending-write byte ceiling.

The index path is now provably fast and bounded (one small MDBX write per tx, in the same per-submodule transaction as the existing index write — crates/domain/src/models/storage_module.rs:1403), so a huge tx can no longer stall later blocks' indexing or Publish promotion. The body path becomes a durable work queue (PendingBodyMigrationsByOffset, crates/database/src/submodule/tables.rs:68) drained by a new worker (crates/actors/src/chunk_migration_service/body_worker.rs:171) that survives restarts, paces itself with a per-pass write budget (body_worker.rs:41), and backs off at a configurable in-memory byte ceiling (body_worker.rs:62) rather than an unbounded queue.

Road not taken: the PR could have kept body writes synchronous but chunked/streamed within a bounded time budget per on_block_migrated call (spreading one huge tx's writes across several ticks while still blocking new indexes behind it, just less badly). Instead it fully decouples indexing from body copying via a durable job table — this buys unconditional forward progress on indexing at the cost of a new invariant to maintain (job row ⇔ index row, enforced by the shared transaction) and a new failure mode to design for (a job that can never be sourced, handled by an 8-attempt retirement policy that hands the hole to data sync, body_worker.rs:35).

Bundled into the same PR: making handle_message infallible so one bad block can't kill the whole service (chunk_migration_service.rs:115); pausing all storage-module data writes during network-partition rollback so the body worker/data sync/chunk ingress can't race the rollback (block_migration_service.rs:724); and purging orphaned body-migration jobs alongside the existing index purge in that same rollback (block_migration_service.rs:833).

Delta semantics

Contract-level changes

  • Durability timing weakens. Previously a caller could assume that once BlockMigrated handling returned, every migratable chunk body was already on disk (or explicitly abandoned to data sync). Now bodies land "typically within one worker pass plus one storage-service flush" after indexing — an unbounded-in-the-worst-case, best-effort window. Reads during that window must be served from the chunk cache, not the storage module.
  • StorageModule::write_chunk gains a return value (() → bool, storage_module.rs:1252): false means a Data-typed write was refused because the module is paused. Entropy writes always return true.
  • New error variant WriteDataChunkError::WritesPaused on write_data_chunk, mapped by every caller into an advisory/non-penalizing outcome rather than a hard failure (chunk ingress → Advisory(Overloaded), chunks.rs:574; migration → a non-error-level log, chunk_migration_service.rs:576).
  • New signature parameter: index_transaction_data(&self, data_tx, tx_path, chunk_range, block_height: u64) — every call site across the codebase (and its tests) was updated; a reorg can now purge a block's jobs by the block_height stamped at index time.
  • New config surface: storage.max_pending_write_bytes: Option<u64> (config/node.rs:471), validated to reject Some(0) (config/mod.rs:83). No storage schema bump: the new MDBX table is registered in SubmoduleTables::ALL and reth/MDBX creates missing tables lazily on env open, so existing submodule DBs pick it up on next start with no migration step.
  • New concurrency primitive: per-module data_writes_paused: AtomicBool, gated under the same pending_writes write lock used for inserts (storage_module.rs:621), so a pause taken mid-race with a writer's own pre-check still wins — the writer's insert and the pause flag can never observably interleave the wrong way.

Weakened, not broken The most consequential row above is the first: the PR trades "body durable before on_block_migrated returns" for "body durable eventually, sourced from cache or a durable replica, else explicitly left for data sync." That trade is the whole point of the fix, and the fallbacks are real — but it does move a previously-synchronous guarantee onto a background component with its own retry/backoff/retirement policy. Cross-file impact

  • crates/actors/src/chunk_ingress_service/chunks.rs:566-582 — write_data_chunk's new WritesPaused variant is caught and remapped to the pre-existing AdvisoryChunkIngressError::Overloaded (already used for capacity backpressure, chunks.rs:910), so gossip peers/HTTP clients are not penalized for a transient recovery pause. Verified this reuses an existing "advisory, not critical" classification rather than inventing new peer-scoring semantics.
  • crates/actors/src/storage_module_service/mod.rs:134-163 (unmodified by this PR) — now the sole source of the periodic flush that used to also run inline per-tx during migration. The body worker's tests explicitly stand in for this tick (force_sync_pending_chunks) rather than relying on it, so the worker's own tests don't depend on this timing, but production behavior does.
  • crates/actors/src/cache_service.rs (unmodified) — checked both chunk-eviction paths against the new deferred-body window: prune_durably_migrated_chunk_bodies (capacity-triggered) gates deletion on storage_module.durable_tx_offsets_for_data_root per offset, so it cannot outrun the body worker. prune_data_root_cache (epoch-triggered, unconditional delete_cached_chunks_by_data_root) is gated on a data_root's included_height against an epoch-scale slot-expiry horizon, which is far longer than any realistic body-migration backlog. Neither path appears to race the new deferred body writes — see Open Questions for whether this was verified deliberately or is incidental.
  • Every non-test caller of write_chunk in production code paths (packing_service/strategies/{cpu,cuda,remote}.rs) only ever writes ChunkType::Entropy, which the new pause gate ignores by design — confirmed by grepping every call site; the new bool return is therefore inert in production today (see Review-focus #4).
  • crates/domain/tests/storage_module_index_tests.rs, crates/actors/tests/data_sync_test.rs, crates/actors/src/packing_service/mod.rs, crates/domain/src/models/chunk_provider.rs — mechanically updated for the new index_transaction_data arity and the new StorageSyncConfig.max_pending_write_bytes field; no behavior change in these files themselves.

Review-focus map

1 · High likelihood, moderate severity body_worker.rs:35 / body_worker.rs:41 — the whole point of this PR is that a huge tx (or a burst of large txs) can leave bodies pending for many blocks. The read path for such an offset — chunk cache, then (Publish only) the durable Submit replica — is bounded by MAX_BODY_MIGRATION_ATTEMPTS = 8 no-progress passes before the job is retired and the hole handed to data sync. Concrete scenario: a burst of several multi-GB Submit txs lands in consecutive blocks under sustained load; the per-submodule 512-writes/pass budget and pending-write ceiling mean the backlog drains slower than 8 passes' worth of wall-clock time for the tail of the backlog; those jobs retire to data sync even though their bodies were sitting in the local chunk cache the whole time and would have been sourced correctly on pass 9+. This is "fail open to a slower path" rather than data loss, but it changes how much load lands on data sync under exactly the failure mode this PR targets, and there is no telemetry correlating retirements with backlog depth beyond the existing counters. Worth a dedicated code-review / load-test pass to confirm the retirement threshold and pacing knobs are tuned for the incident's actual scale (the n3 tx was ~16.9k chunks) rather than just the unit-test scale (3 chunks).
2 · Medium likelihood, low-moderate severity body_worker.rs:563 — write_offset's guard Err(_) if self.sm.data_writes_paused() => return Ok(WriteAttempt::Paused) catches any error type as long as the module happens to be paused at the moment it's checked, not just errors actually caused by the pause. Concrete scenario: if a future code path calls pause_data_writes outside of apply_rollback (today the only caller), or if a genuine, pause-unrelated error (e.g. a corrupted index entry) coincides with an in-flight rollback pause on the same module, the job is silently deferred with zero attempt penalty and no diagnostic, rather than being logged and eventually retired. Today this is masked because the only current pause site (network-partition rollback) also purges the corresponding job row via purge_pending_body_migrations_in_range, so the misclassified job usually disappears before the distinction matters — but the coupling between "this error happened to occur while paused" and "this error was caused by being paused" is implicit, not enforced by the error type.
3 · Design pressure block_migration_service.rs:747 — PausedDataWrites::pause is built from every storage module the node runs (storage_modules_guard.read().iter().cloned().collect()), not just the modules whose ranges the rollback touches (rollback_infos). Combined with the new chunk-ingress mapping to Advisory::Overloaded, a network-partition rollback now makes chunk uploads to every partition on this node advisory-fail for the rollback's duration, including ledgers/slots entirely unrelated to the reorg. The surrounding comment frames this as a deliberate simplicity tradeoff given the file's documented crash-unsafety constraints, so this reads as an accepted design choice rather than an oversight — but the blast radius (node-wide, not rollback-scoped) is worth confirming was intended, especially for a many-partition miner where reorgs are not vanishingly rare.
4 · Low severity, latent storage_module.rs:1252 — write_chunk's new bool return (queued vs. refused-by-pause) is not #[must_use], so a caller can silently ignore it exactly like the old () signature. Every current production call site only ever writes ChunkType::Entropy (unaffected by the pause gate), so this is inert today; a future ChunkType::Data caller that bypasses write_data_chunk and calls write_chunk directly would silently drop bytes under pause with no compiler nudge to check the result.

Items 1–2 look serious enough to be worth a dedicated /code-review pass to verify against real backlog-scale data (chunk counts, disk throughput) rather than the unit-test fixtures' 3-chunk scale; items 3–4 are lower-severity design notes for the author to confirm rather than fix.

Open questions

  • Was the interaction between this PR's deferred body-write window and cache_service.rs's two chunk-eviction paths (prune_durably_migrated_chunk_bodies, durability-gated; prune_data_root_cache, epoch/slot-expiry-gated) explicitly reasoned about and tested, or is their current safety incidental to how each happens to be gated? Neither file is touched by this diff.
  • The PR's own test plan leaves "Deploy to devnet n3" unchecked, with the specific acceptance criteria being body_pending_jobs draining and Publish Data climbing from 416,450 toward 512,636. Has that redeploy happened since this PR was opened, and did the backlog drain at a rate consistent with the chosen defaults (512 writes/submodule/pass, 2-flush-batch ceiling)?
  • Is MAX_BODY_MIGRATION_ATTEMPTS = 8 (paced at BODY_MIGRATION_TICK = 2s between idle ticks, but back-to-back while progress is made) sized against the actual incident scale, or was it chosen primarily to keep the unit tests fast? For a job with no local source at all, retirement to data sync happens quickly regardless of tx size — was that fast-fail intentional, or should "no source" and "too slow to keep up" be distinguished with different budgets?
  • PausedDataWrites pausing every storage module rather than only the rollback-affected ones (Review-focus #3): deliberate scope, or would scoping it to rollback_infos' modules be a safe follow-up?
