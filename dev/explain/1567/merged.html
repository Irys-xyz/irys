Chunk migration: index path split from background body migration

PR #1567 · Irys-xyz/irys · summary mode · repo checkout at 3db6f37
What & why Change map Behavior changes Watch out for

What it does & why

What it does: Chunk migration used to index a block's transactions and copy every chunk body into the storage module in one synchronous pass. This PR splits that into two decoupled paths: an index path that commits `tx_path`/`data_root` mappings in block order (MDBX-only, no chunk bytes touched) plus a small durable job row per submodule saying bodies are still owed, and a new background body worker that drains those job rows at disk speed, sourcing bytes from the chunk cache or (for Publish) the durable Submit replica, paced by a per-pass write budget and a configurable pending-write byte ceiling.

Why: stated intent (PR description / commit messages) — a single 4.43 GiB Submit tx at block 29875 saturated a storage module's packing writes so its bodies never finished migrating; because indexing and body-writing were one blocking step, every later block's indexes (including Publish promotions that grew the ledger from 416,450 to 512,636 chunks) never got indexed, and data sync parked the whole span on MissingDataRootIndex.

Behavior changes

  • Chunk-body writes for a migrated block no longer complete before BlockMigrated returns → they land asynchronously afterward; reads for those offsets in the intervening window are served from the chunk cache instead of the storage module.
  • A migration failure for one block previously unwound and terminated the chunk-migration service for the node's lifetime → now it is logged and later blocks still migrate; the failed block's indexes are only restored by an index-heal pass.
  • Writing a chunk to a storage module during network-partition recovery previously had no defined "paused" outcome → now write_data_chunk/write_chunk explicitly return WritesPaused/false, and chunk ingress treats that as success (gossip still runs) rather than failing the request.
  • storage.max_pending_write_bytes = 0 in config was previously accepted → now Config::validate rejects it at startup.
  • StorageModule::index_transaction_data and process_ledger_transactions gained a required block_height parameter (only when data_root and block_height both match can a job be settled or retired).

Watch out for

  • crates/actors/src/chunk_migration_service/body_worker.rs:461 — drain_job snapshots pending_write_bytes() once per job and checks it against the shared per-module ceiling (line 490) without re-reading the live value; because a module's submodules are each drained by their own concurrent spawn_blocking task sharing the same StorageModule, two or more submodule tasks can each observe the ceiling as not-yet-reached and enqueue up to their own budget simultaneously — the module's actual pending-write memory can transiently overshoot the configured ceiling before the next pass's fresh read corrects it (worth a dedicated code-review pass).
  • crates/actors/src/data_sync_service.rs:60 — unlike chunk ingress and the migration path, this call site has no explicit arm for WriteDataChunkError::WritesPaused; it falls into the generic Other(e.to_string()) branch, so every data-sync write that lands during a recovery pause logs a "write failed" warning and increments chunk_write_failed_total{reason="other"} even though the condition is expected and transient.
  • crates/actors/src/block_migration_service.rs:747 — recovery pauses data writes on every storage module for the whole rollback, not only the modules whose ranges are being rewritten, so an unrelated partition's body-worker/data-sync/ingress writes stall for that entire window. The code comment states this is deliberate (simplicity over precision), but it widens the blast radius of a rollback beyond the ranges actually being touched.
