Cutting irys-types loose from the Reth umbrella crate

What it does: irys-types stops depending on the umbrella reth crate and on reth-transaction-pool (it only needed that for PeerId, now alloy_primitives::B512). A new db feature, default‑on, gates the expensive part — reth-db/reth-db-api/reth-chainspec/reth-tasks (MDBX, mdbx-sys, vendored OpenSSL) — behind #[cfg(feature = "db")], so a git consumer like gateway can build with default-features = false and skip all of that. SHA‑256 moves from openssl to sha2, and signature recovery moves from reth_primitives_traits to alloy_primitives. reth-node-bridge's production adapter now wraps the launched FullNode directly instead of reth_e2e_test_utils::NodeTestContext, so production no longer builds the e2e test harness. Riding along in the same PR (per the commit log, not the PR description): a fix that parks ingress proofs anchored to a not‑yet-imported block instead of hard‑rejecting them, a balance‑fetch fix, and several test-flakiness fixes for a 3‑node promotion test.

Why: the PR description states the umbrella reth/reth-transaction-pool deps pulled roughly 100 Reth crates into packing, VDF, and any git consumer of irys-types — with default db on, packing still sees ~23 Reth crates, but --no-default-features drops that to 5 with no mdbx-sys and no Reth-vendored OpenSSL. The bundled ingress-proof/test fixes are stated in the commit messages as CI-flake root causes discovered while stabilizing the branch, not part of the stated Reth-slimming goal.

Behavior changes

  • Gateway/git consumers of irys-types: before → pulled in the full Reth/MDBX/OpenSSL graph unconditionally. After → building with default-features = false compiles only 5 Reth crates (reth-codecs, its derive, ethereum-primitives, primitives-traits, zstd-compressors), no mdbx-sys, no vendored OpenSSL. Default builds (the node workspace) are unaffected since db is on by default.
  • Gossiped ingress proofs anchored to a not-yet-imported block: before → hard-rejected as InvalidAnchor, gossip treated it as bad data and did not retry, so a lagging peer could get stuck below the quorum of proofs indefinitely. After → parked as UnknownAnchor, acked (so the sender isn't penalized by gossip), and automatically retried once the anchor block enters the block tree or is confirmed. A too-old anchor is still a hard reject.
  • Balance lookup for a never-seen account (get_balance_irys_canonical_and_pending): before → None from the state provider surfaced as BalanceFetchError. After → treated as a zero balance, so funding validation reports Unfunded instead of an internal error for a signer that has never had a balance.
  • CI's cargo check step: before → ran under RUSTFLAGS="-D warnings", so any rustc warning failed the check job. After → runs plain cargo xtask full-check (no warnings deny); only the separate cargo xtask clippy job now denies warnings, via appended clippy args rather than rustflags.

Watch out for

crates/types/Cargo.toml:7 No CI job builds irys-types with --no-default-features (checked with grep against .github/workflows/rust.yml) — the "5 Reth crates, no mdbx" claim in the PR description was verified once by hand, not by an ongoing gate. A future change that adds a non-#[cfg(feature = "db")] use of a gated symbol under one of these files would only be caught by whoever next runs the manual check, and gateway (an external consumer) would find out at its own build time (worth a dedicated code-review pass to confirm nothing was missed).
.github/workflows/rust.yml:220 The check job no longer denies warnings at all (only clippy does, and clippy uses a different rustc driver). A warning rustc emits but clippy doesn't would now pass CI silently where it previously failed the check job.
pending_ingress_proofs.rs:8 Parked proofs live only in an in-process Mutex-guarded map, capped at 512 entries, with no persistence. A node restart while proofs are still parked drops them (the sender must re-gossip), and once 512 distinct unknown-anchor proofs are queued, new ones are rejected with Overloaded rather than parked — worth confirming the cap is sized for realistic lag windows.
adapter.rs:112 get_balance_irys_canonical_and_pending now folds "account not found" and "zero balance" into the same Ok(zero) result. That's the intended fix for the funding-validation caller, but any other current or future caller that needs to distinguish "never seen this address" from "confirmed zero balance" loses that distinction silently.
adapter.rs:45 The mechanical .reth_node.inner.X → .X rewrite touches call sites across reth_service.rs and block_validation.rs; a wide, repetitive rewrite like this is exactly where a missed or over-eager replacement hides (a fully compiling but semantically wrong field/method swap), so it's worth a dedicated code-review pass over those call sites specifically.
