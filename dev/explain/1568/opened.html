Intent & approach

irys-types previously pulled in the umbrella reth crate and reth-transaction-pool purely for PeerId, which meant every downstream build of irys-packing, irys-vdf, and any git consumer of irys-types (gateway) compiled ~100 Reth crates it never used. This PR does two things in sequence, matching its two commits:

  • Commit 1 replaces the umbrella dependency with leaf crates and rewrites crates/reth-node-bridge/src/adapter.rs:35 IrysRethNodeAdapter to wrap the launched FullNode (RethNode) directly, instead of wrapping reth_e2e_test_utils::NodeTestContext — the e2e test harness that had been quietly linked into the production node-bridge build. PeerId becomes alloy_primitives::B512.
  • Commit 2 introduces a db feature on irys-types (crates/types/Cargo.toml:7), default-on, that gates reth-db/reth-db-api/reth-chainspec/reth-tasks (MDBX, mdbx-sys, vendored OpenSSL) behind it. SHA-256 hashing moves from openssl::sha to sha2, and ECDSA signer recovery moves from reth_primitives_traits::crypto::secp256k1::recover_signer to alloy_primitives::Signature::recover_address_from_prehash — both were only reachable through the umbrella/leaf Reth deps being removed.

Road not taken: the PR could have split irys-types into a slim core crate plus a separate Reth-dependent extension crate, avoiding #[cfg(feature = "db")] scattered across ~15 files. It chose in-place cfg-gating instead — cheaper to land, but it leaves the crate's compile surface implicit in a long tail of per-impl attributes rather than a visible module boundary, and the PR description is explicit that true zero-Reth is still blocked by the Compact orphan rule and gossip Block/Header types staying unconditional.

Stated intent vs inferred The PR description states the crate-count numbers directly (100 → ~23 with default db, 5 with --no-default-features) and that these were verified with cargo check -p irys-types --no-default-features and cargo check --workspace --tests --locked. Everything about why gateway needs this is stated intent; the choice of cfg-gating over a crate split is inferred from the diff shape, not stated.

Feature-gating contract (irys-types db feature)

New default-on feature at crates/types/Cargo.toml:7. With it disabled, irys-types loses: reth_db::table::{Encode,Decode} impls for IrysAddress, DataLedger, IrysPeerId, U256, H256, PartitionChunkOffset, UnixTimestamp/UnixTimestampMs; Compress/Decompress for IngressProofV1; the chainspec, app_state, and arbiter_handle modules entirely; and the PeerNetworkError::Database variant plus its From<DatabaseError> impl. Compact (from reth-codecs) and the ethereum primitive types stay unconditional — they're the orphan-rule / gossip-type floor the PR description calls out as the reason true zero-Reth isn't reachable yet.

Wire-type substitution

reth_transaction_pool::PeerId is replaced by alloy_primitives::B512 in RethNetworkConfig::peer_id and RethPeerInfo::peer_id (crates/types/src/peer_list.rs:295). Both are 64-byte fixed-size types (reth_transaction_pool::PeerId is itself a B512 alias upstream), so the on-wire/Compact-encoded representation is unchanged; the Compact impl is updated in place to call B512::from_compact.

Cryptographic primitive substitution (consensus-relevant)

SHA-256 (hash_sha256, hash_ingress_sha256 at crates/types/src/merkle.rs:710, and compute_solution_hash at crates/types/src/block.rs:905) moves from openssl::sha::Sha256 to the sha2 crate. ECDSA signer recovery (IrysSignature::recover_signer at crates/types/src/signature.rs:52) moves from reth_primitives_traits::crypto::secp256k1::recover_signer to alloy_primitives::Signature::recover_address_from_prehash. Both are standard, widely-used implementations of the same algorithms, and both feed compute_solution_hash / ingress-proof verification / transaction-signer recovery — all of which must be byte-identical across every node for consensus to hold.

Review-focus map

1. crates/reth-node-bridge/src/adapter.rs:69 — balance reads switched from a raw state-provider lookup to the full RPC balance() handler recommend code-review pass
Concern: get_balance/get_balance_irys used to call a custom IrysRethLoadStateExt::balance that read StateProviderBox::account_balance directly and defaulted any error or missing account to zero. They now call the standard EthApiServer::balance RPC handler, which resolves pending/safe/finalized state through a different internal path.
Failure scenario: a BlockId that resolves differently between the two implementations (e.g. a very recent block during a reorg window, or a pending-block query) causes get_balance to return a different balance or a hard RPC error where the old path returned a defaulted zero — this would show up as a spurious funding-check failure or an incorrect balance in a test/gossip path, not a compile error, so it is easy to miss.
2. crates/p2p/src/gossip_client.rs:108 — non-cfg-gated match on a now-feature-gated enum variant
Concern: PeerNetworkError::Database became #[cfg(feature = "db")] in crates/types/src/peer_list.rs:631, but the match arm consuming it was left ungated.
Failure scenario: any future build that compiles irys-p2p against irys-types with default-features = false (the exact configuration this PR asks the gateway project to adopt) fails to compile with "no variant named Database" — a hard break the PR's own stated goal (gateway using default-features = false) could trigger if gateway ever needs irys-p2p.
3. crates/types/src/block.rs:905 / crates/types/src/merkle.rs:710 — consensus-critical hash implementation swap has no dedicated golden-vector test
Concern: compute_solution_hash, hash_sha256, and hash_ingress_sha256 switch from openssl::sha to sha2. The signature-recovery swap in the same commits is covered by hardcoded JS-client parity vectors (signature.rs:296), but these hash helpers are only exercised by self-consistency tests (hash-then-compare-with-itself), not a fixed expected output.
Failure scenario: both libraries are standard SHA-256 implementations so a mismatch is unlikely, but if one existed it would silently change PoA solution hashes and ingress-proof hashes between nodes running old vs. new binaries — a consensus-fork risk with no test to catch it, rather than a functional bug with an obvious symptom.

These are attention pointers, not confirmed defects. Item 1 and 2 in particular are worth a dedicated /code-review pass before merge; item 3 is lower-likelihood but higher-severity if it ever manifested, given the "deterministic output" requirement this codebase holds itself to.
