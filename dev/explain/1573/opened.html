Intent & approach

A handshaked peer can request an arbitrary historical BlockBody via either the gossip GetData POST (handle_data_request_inner) or the PullData POST (handle_pull_data/handle_pull_data_v1), both of which resolve into gossip_data_handler.rs:849 (handle_get_data) or gossip_data_handler.rs:889 (handle_get_data_sync). Both funnel into resolve_data_request → get_block_body, whose fallback path reconstructs the body from the mempool and consensus DB via build_block_body_for_processed_block_header (gossip_data_handler.rs:1307) — the expensive path the PR title targets. The existing dedup/score gate in DataRequestTracker::check_request throttles score accrual per peer but still returns ServeOnly (i.e. should_serve() == true) for duplicate requests inside the window (rate_limiting.rs:158 onward), so a single peer repeating a body request at line rate is still fully resolved every time — no per-body-reconstruction ceiling existed before this change.

The fix adds a shared tokio::sync::Semaphore (block_body_semaphore) to GossipDataHandler, sized from a new config knob max_concurrent_block_body_serves (default 8, 0 = unlimited via Semaphore::MAX_PERMITS) at gossip_data_handler.rs:81. A new helper, acquire_block_body_permit (gossip_data_handler.rs:909), is a no-op (Ok(None)) for every GossipDataRequestV2 variant except BlockBody; for a body request it does a non-blocking try_acquire_owned() and maps failure to GossipError::RateLimited. Both entry points call this helper after the existing dedup/score check but before resolve_data_request, so admission is gated on the semaphore, not on request identity or recency.

Road not taken: the cap could have lived inside resolve_data_request or get_block_body itself, scoped to only the expensive reconstruction branch (cache/tree hits are cheap and don't need a permit). Instead the permit is held for the entire resolve_data_request call, including the cheap block-pool-cache and block-tree-read paths that don't touch the DB. This is simpler (one call site, one permit type per request) but means cheap cache hits still consume a concurrency slot for their duration, and — more importantly — the permit is held across a call that itself acquires block_tree.read(), a blocking (non-async-aware) lock; see the review-focus entry below.

Contract delta

  • New concurrency invariant: at most max_concurrent_block_body_serves (default 8) BlockBody resolutions may be in flight across all gossip entry points and all clones of GossipDataHandler simultaneously, because the semaphore is Arc-shared and explicitly re-Arc::cloned in Clone::clone (gossip_data_handler.rs:133). Other request kinds (headers, execution payloads, transactions, chunks) are exempt — acquire_block_body_permit returns Ok(None) for them, so they cannot be starved by the body cap.
  • Error-contract widening: both handle_get_data and handle_get_data_sync can now return Err(GossipError::RateLimited) for a reason unrelated to peer identity or request recency — pure capacity exhaustion. Callers already treat any RateLimited uniformly (mapped to RejectionReason::RateLimited in server.rs), so no caller needs new error-handling code, but the meaning of a RateLimited response to a well-behaved peer has changed: it can now mean "the node is busy," not "you are being throttled."
  • Ordering/scope: the permit is acquired via a scoped let _permit = … binding at gossip_data_handler.rs:870 (inside a block expression) and at gossip_data_handler.rs:904 (function-scoped), so it is held for the full duration of resolve_data_request, released on every exit path (success, ?-propagated error, or task cancellation/abort) via `Drop` on `OwnedSemaphorePermit` — this is the property the four concurrency tests at the bottom of the diff exist to pin down.
  • Config compatibility: P2PGossipConfig carries #[serde(deny_unknown_fields, default)] at the struct level (node.rs:785), so old TOML configs missing the new key deserialize with the struct-level Default (8), not a zero value or a deserialization error — verified by the new block_body_serve_cap_is_eight_when_the_key_is_absent test. An explicit 0 in config is preserved as "unlimited," not coerced to the default.

Cross-file impact

  • gossip_service.rs:356 — the production GossipDataHandler construction site now builds the semaphore from config.node_config.p2p_gossip.max_concurrent_block_body_serves; any future field added to GossipDataHandler alongside this one would need the same three-site update (this one plus the two below), which the compiler enforces via struct-literal exhaustiveness but is worth noting as a recurring maintenance point.
  • tests/util.rs:373 and tests/util.rs:386 — both test-fixture constructors (data_handler_stub, data_handler_with_stubbed_pool) now read the same config field, so any existing test that builds a handler through these helpers and exercises many concurrent body requests inherits the cap (default 8) instead of running unthrottled; no such test appears to previously assume unlimited concurrency in this crate.
  • server.rs:1691, server.rs:1789, server.rs:1826 — the three HTTP handlers calling into handle_get_data/handle_get_data_sync already match on Err(GossipError::RateLimited) and translate it to RejectionReason::RateLimited; none required a code change because the new failure mode reuses the existing error variant, but they also cannot distinguish "peer throttled" from "server saturated" in logs or metrics — both look identical to a caller.
  • get_block_body (gossip_data_handler.rs:1288) is unchanged and still takes block_tree.read() (a blocking, non-`.await`-yielding lock per the test comment at gossip_data_handler.rs:269) inside the region now guarded by the permit — the permit's lifetime was extended to cover an existing blocking call it didn't previously need to coexist with at a bounded concurrency.

Review-focus map

Mediumgossip_data_handler.rs:869 — the permit is held across the entire resolve_data_request call for every BlockBody request, including the cheap block-pool-cache hit and the block-tree-read hit, not just the expensive DB-reconstruction fallback it was introduced to bound.
Failure scenario: 8 concurrent requests for a body that's already cached in the pool (near-instant to resolve) will still occupy all 8 permits for the duration of those cheap lookups; if a 9th request for a genuinely expensive, uncached historical body arrives in that window, it is rejected as RateLimited even though the node had ample spare capacity for the expensive path specifically. The cap conflates "concurrent cheap serves" with "concurrent expensive reconstructions," which is a coarser signal than the PR's stated goal ("limits database reconstruction of historical bodies," per the new field's doc comment at node.rs:798).
Mediumgossip_data_handler.rs:1301 — an admitted body serve now holds an owned semaphore permit while blocking on block_tree.read(), a lock that is not tokio-aware; the accompanying test at gossip_data_handler.rs:272 is explicit that this blocks the worker thread, not just the task.
Failure scenario: if a writer holds block_tree's write lock for an extended period (e.g. during reorg processing or block-tree pruning) while up to 8 body-serve tasks each block a runtime worker thread waiting on the read lock, those 8 workers are unavailable for other async work on a runtime with few worker threads, potentially starving unrelated tasks scheduled on the same runtime — the semaphore caps how many requests can pile up this way, but doesn't change the fact that each one parks a whole worker rather than yielding.
Lowgossip_data_handler.rs:81 — the "0 means unlimited" convention is implemented via Semaphore::MAX_PERMITS rather than bypassing the semaphore entirely.
Failure scenario: this is functionally unlimited in practice (a huge permit count), but every BlockBody request still pays the cost of an atomic try_acquire_owned/release pair even when the operator intended "no limiting at all" — negligible overhead, worth a one-line note only if this path turns out to be hotter than expected.

These are attention pointers from static reading, not verified findings — a dedicated code-review pass (/code-review) would be the right next step to confirm whether the runtime's worker-thread pool sizing makes the second entry a practical concern in this deployment.

Open questions

  • Was scoping the permit to the whole of resolve_data_request (rather than only the DB-reconstruction branch inside get_block_body) a deliberate simplicity trade-off, or should the cap move down to build_block_body_for_processed_block_header specifically so cache/tree hits don't consume a slot?
  • Is a default of 8 concurrent body serves calibrated against a specific measurement (mempool/DB reconstruction latency, number of expected simultaneously-syncing peers), or is it a round-number starting point pending production tuning?
  • The PR description states the "Before" behavior as the dedup window still serving repeated requests at line rate — was a per-peer cap (in addition to or instead of this global cap) considered, so one abusive peer can't consume all 8 slots and starve legitimate sync traffic from other peers?
