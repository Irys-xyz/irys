Intent & approach

Config::validate already rejects num_partitions_per_slot == 0 (crates/types/src/config/mod.rs:176-179) because it drives log10(0)/NaN math in genesis capacity computation. It had no analogous guard for num_partitions_per_term_ledger_slot, the independently-configurable replica count used only by the term ledgers (OneYear/ThirtyDay) (crates/types/src/config/consensus.rs:99-101). Zero in that field is not a crash hazard — it is a pricing hazard: it multiplies the term-fee's replica cost down to zero, which then falls back to the configured minimum USD fee for any OneYear/ThirtyDay storage request, regardless of size or duration.

The fix adds one symmetric ensure! immediately after the sibling num_partitions_per_slot check (crates/types/src/config/mod.rs:180-184), plus one new #[case] row in the existing rstest table that already documents "runtime panic / freeze configs that used to pass validate()" (crates/types/src/config/mod.rs:1935-1948). Nothing else in the diff changes.

Approach chosen: fail fast at config-load time, gating node startup (config.validate()?; at crates/chain/src/chain.rs:567), rather than guarding inside the pricing function itself.

Road not taken The zero-guard could instead live inside calculate_term_fee / replica_count (crates/types/src/storage_pricing.rs:510), which would protect every current and future caller regardless of how its replica count was produced. The PR instead keeps the invariant at the one config-loading path, mirroring the sibling num_partitions_per_slot check's placement. That is consistent with the existing style in this file but leaves the pricing function itself trusting its input unconditionally.

Compatibility

Any config that previously set num_partitions_per_term_ledger_slot = 0 and passed validation will now fail at startup via crates/chain/src/chain.rs:567. None of the in-repo fixtures hit this: the docker data-sync configs set it to 3 (e.g. docker/tests/data-sync/configs/irys-1.toml:104), the testnet template sets it to 1 (crates/config/templates/testnet_config.toml:115), and every ConsensusConfig::testing()-style default in crates/types/src/config/consensus.rs:786, 883, 1010 sets 10, 1, and 10 respectively — none are zero, matching the PR description's claim that NodeConfig::testing() still passes. This is a breaking change only for a deployed config that had 0 in the field already, which is exactly the case this PR intends to make unrepresentable.

Error contract

ensure! returns the same error type (anyhow-style, propagated as eyre::Result by the caller) as every other check in this function, so no new error variant or handling path is introduced — the caller at crates/chain/src/chain.rs:567 already propagates whatever validate() returns.

Cross-file impact

The diff touches only crates/types/src/config/mod.rs. It matters because four consumers currently trust num_partitions_per_term_ledger_slot as a replica-count multiplier without any local zero-guard; none of them are modified by this PR — they are the reason the invariant matters, not sites this PR changes.

  • crates/api-server/src/routes/price.rs:230 — the public /price endpoint reads the field as replica_count and feeds it straight into calculate_term_fee (price.rs:232); relies entirely on the config having passed validate() at startup.
  • crates/actors/src/tx_selector/mod.rs:714 — mempool transaction selection recomputes the expected term fee from the same field to decide whether a pending tx's declared term_fee is sufficient before including it in a block (mod.rs:715-728).
  • crates/actors/src/mempool_service/data_txs.rs:397 — the same check runs again at ingress time, before a term-ledger tx is admitted to the mempool at all.
  • crates/actors/src/block_validation.rs:6133 — block state-validation's calculate_term_storage_base_network_fee (defined at block_validation.rs:5988) takes the same field as a direct argument; this path runs on every block a validating node processes, not just on the local node's own txs.

All four sites call the same underlying calculate_term_fee (storage_pricing.rs:510), which multiplies duration-adjusted cost by replica_count via storage_pricing.rs:325-332 (safe_mul(self.amount, U256::from(replicas)) — a zero multiplicand silently yields zero, no error) and then clamps up to config.minimum_term_fee_usd whenever the computed fee is below it (storage_pricing.rs:544-548). This is the exact mechanism the PR description names: replica_count=0 → base_fee=0 → clamp to minimum, regardless of the requested byte count or storage duration.
