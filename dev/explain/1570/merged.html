What it does

POST /v1/chunk used to hold the HTTP response open on a oneshot channel until the chunk ingress worker finished merkle validation, the MDBX cache commit, storage-module write/pack, gossip fan-out, and the ingress-proof check. This PR makes the HTTP response fire as soon as the chunk body is admitted onto the existing ingress channel — a new enqueue_http_chunk helper (crates/actors/src/chunk_ingress_service/http_admission.rs:24) gates admission with two semaphores and a timeout, and the actual chunk processing continues asynchronously in the background. Gossip and data-sync ingest paths are untouched: they still block on the oneshot because they use the result to score peers and decide whether to retry.

To keep the async handoff safe, ChunkIngressMessage::IngestChunk gained a drop-guard field that holds the admission permit until the worker is done, the chunk-ingress service now backlogs saturated HTTP admissions instead of parking its receive loop (which would otherwise queue ahead of gossip), and shutdown gained an explicit "stop accepting new HTTP chunks" gate plus a backlog-drain phase.

Why

Stated intent (PR description and the new ADR): the previous contract made "HTTP 200" a durability signal and held Actix worker threads across packing I/O, which is exactly the latency this change removes. The ADR (docs/adr/0001-http-chunk-ack-on-enqueue.md:1) records that ack-on-enqueue was chosen over ack-after-merkle-validation and ack-after-MDBX-commit as the three alternatives considered.

Change map

  • HTTP ack decoupled from processing (crates/api-server/src/routes/post_chunk.rs, crates/actors/src/chunk_ingress_service/http_admission.rs) — post_chunk now calls crates/api-server/src/routes/post_chunk.rs:55 and returns 200 the moment the chunk is admitted onto the channel, instead of awaiting a oneshot for the full ingest result.
  • Admission permit threaded through the message itself (crates/actors/src/chunk_ingress_service.rs, block_validation.rs, facade.rs, several tests) — ChunkIngressMessage::IngestChunk gains a third field, Option<HttpAdmissionGuard> (crates/actors/src/chunk_ingress_service.rs:63), a drop-guard that releases the admission permit once the worker finishes handling the message. Every existing constructor and pattern match on the three-way tuple across the crate was updated, mostly mechanically (adding a trailing None or _).
  • In-service backlog instead of parking on HTTP saturation (crates/actors/src/chunk_ingress_service.rs) — a new NoPermitAction enum (crates/actors/src/chunk_ingress_service.rs:184) distinguishes reply-bearing gossip/data-sync callers (fast-fail Overloaded), HTTP-admitted fire-and-forget chunks (queue on a new http_backlog: VecDeque crates/actors/src/chunk_ingress_service.rs:443), and other control-plane fire-and-forget messages (still park the recv loop on acquire().await). The backlog is drained opportunistically in the same tokio::select! (crates/actors/src/chunk_ingress_service.rs:451).
  • Shutdown correctness gate (crates/actors/src/chunk_ingress_service.rs, chunk_ingress_service/http_admission.rs) — a shared http_ingress_open: Arc<Mutex<bool>> flips to false at the start of shutdown (crates/actors/src/chunk_ingress_service.rs:564); enqueue_http_chunk checks the same flag under the same mutex before and after acquiring a permit (crates/actors/src/chunk_ingress_service/http_admission.rs:36), so a racing enqueue fails fast with ChannelClosed instead of a chunk landing in a channel that stops being drained. Shutdown also grew a dedicated backlog-drain phase (crates/actors/src/chunk_ingress_service.rs:608).
  • New tunables and validation (crates/types/src/config/mod.rs, config/node.rs) — max_http_chunk_admission (default 256), max_http_chunk_waiters (default 32), and http_chunk_admission_timeout_millis (default 5000), each validated non-zero (crates/types/src/config/mod.rs:312).
  • Tests adapted from synchronous to polled assertions (crates/chain-tests/src/utils.rs, multi_node/mempool_tests.rs, integration/cache_service.rs) — new helpers wait_until_chunk_accepted (crates/chain-tests/src/utils.rs:3121) and wait_for_http_chunk_idle (crates/chain-tests/src/utils.rs:3163) replace assertions that used to fire the instant a 200 came back, since a 200 no longer implies the chunk was validated, cached, or even parked yet.

Behavior changes

  • POST /v1/chunk timing: before, the response only returned after merkle validation, the MDBX cache commit, storage-module write/pack, gossip send, and the ingress-proof check all completed. After, it returns as soon as the body is admitted onto the ingress channel (crates/api-server/src/routes/post_chunk.rs:65); everything else happens asynchronously afterward.
  • Per-chunk validation feedback: before, a bad chunk returned a specific status derived from ChunkIngressError — 400 for InvalidProof/InvalidDataHash/InvalidChunkSize/InvalidDataSize/InvalidOffset, 500 for DB/other critical errors, and 200-with-error-body for advisory errors. After, the HTTP layer never learns the outcome of validation — every chunk that is admitted onto the channel gets 200, whether it turns out valid or not (crates/api-server/src/routes/post_chunk.rs:18).
  • New failure modes on the HTTP route: 503 when the admission or waiter semaphore is saturated, or when the admission wait times out (http_chunk_admission_timeout_millis, default 5000ms); 500 only if the ingress channel itself is closed. Malformed JSON is still 400 from the Actix extractor, before this handler runs.
  • Saturation handling for HTTP ingest: before, all fire-and-forget IngestChunk messages parked the service's receive loop on the chunk-lane semaphore when saturated. After, HTTP-origin fire-and-forget chunks instead queue on an in-memory backlog (bounded by the 256+32 admission/waiter permits), so gossip's try_acquire is not queued behind them.

Watch out for

  • 1 crates/api-server/src/routes/post_chunk.rs:65 — a 200 response no longer means the chunk was valid or stored, only that it was admitted to the queue; any external client, integration tool, or internal caller that still reads the HTTP status to decide whether a chunk needs to be re-uploaded will now treat rejected chunks (bad proof, bad offset, oversized) as successes with no signal to act on (worth a dedicated code-review pass to confirm nothing downstream still depends on the old per-chunk status codes).
  • 2 crates/actors/src/chunk_ingress_service.rs:622 — the shutdown backlog-drain loop treats a closed message_handler_semaphore as fatal and breaks immediately, leaving every remaining message still in http_backlog dropped without any notification. Because chunk-lane saturation and semaphore closure are shared with the earlier queued-message drain (line 594), if the semaphore is already closed by the time shutdown reaches the backlog loop, the entire backlog — chunks whose POST already returned 200 — is silently lost in one step.
  • 3 crates/chain-tests/src/multi_node/mempool_tests.rs:381 — preheader_rejects_when_cache_full used to assert the response body directly named the rejection reason; it now infers rejection from the chunk's absence from the pending map and the chunk cache after polling to idle. If a future regression makes the overflow chunk get cached instead of dropped, this test still passes as long as it isn't cached by the time the poll settles — a strictly weaker guarantee than the removed synchronous body assertion.
  • 4 crates/actors/src/chunk_ingress_service/http_admission.rs:24 — worst-case retained HTTP chunk bodies are (256 + 32) × 1 MiB at the JSON size limit, per the new ADR. That memory footprint is only as safe as the two new config defaults; operators changing max_http_chunk_admission or max_http_chunk_waiters upward without accounting for chunk size change this bound directly.
