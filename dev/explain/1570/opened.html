Intent & approach

POST /v1/chunk previously blocked an Actix worker on a oneshot until handle_chunk_ingress_message finished merkle validation, the MDBX cache write, storage-module packing, gossip send, and the ingress-proof check (docs/adr/0001-http-chunk-ack-on-enqueue.md:7). This PR moves the acknowledgement point earlier: the handler now returns 200 as soon as the chunk is admitted onto the existing unbounded chunk_ingress channel (crates/api-server/src/routes/post_chunk.rs:55-69), turning the public HTTP contract from a durability signal into an admission signal. Gossip and data-sync keep the old oneshot contract because they score peers and retry on ChunkIngressError (docs/adr/0001-http-chunk-ack-on-enqueue.md:9).

The approach layers two independent admission controls rather than one:

  • HTTP-only gate (enqueue_http_chunk, crates/actors/src/chunk_ingress_service/http_admission.rs:19) — a max_http_chunk_admission semaphore (default 256) held from enqueue until the ingress worker finishes, plus a second max_http_chunk_waiters semaphore (default 32) that bounds how many already-decoded Json<UnpackedChunk> bodies may block on the first semaphore, since Actix decodes the body before the handler gets a chance to apply backpressure.
  • Chunk-lane gate (pre-existing message_handler_semaphore inside ChunkIngressService) — now has a third routing outcome. On saturation, reply-bearing messages still fail fast with Overloaded; fire-and-forget chunk messages (the new HTTP-admitted case) go onto an in-service VecDeque backlog instead of parking the receive loop; other fire-and-forget control-plane messages still park (crates/actors/src/chunk_ingress_service.rs:253-261).

The road not taken, named explicitly in the ADR: ack after merkle validation (keep 400 for bad proofs) or ack after the MDBX commit introduced in #1558 (keep synchronous durability, async packing only) (docs/adr/0001-http-chunk-ack-on-enqueue.md:11-15). The PR takes the most aggressive option: ack on enqueue, with no validation guarantee at all in the HTTP response.

Other contract changes

  • New enum shape. ChunkIngressMessage::IngestChunk gained a third tuple field, Option<HttpAdmissionGuard> (crates/actors/src/chunk_ingress_service.rs:63-67). All six production/test match sites in the diff were updated; the lens found no missed call site.
  • New failure modes on the HTTP route. post_chunk can now return 503 (WaitersSaturated, AdmissionTimeout) in addition to the pre-existing 500/400, via enqueue_error_status (crates/api-server/src/routes/post_chunk.rs:18-25). Any client that only handled 400/500/200 needs to treat 503 as retryable.
  • Config compatibility is preserved. MempoolNodeConfig carries #[serde(deny_unknown_fields, default)] at the struct level (crates/types/src/config/node.rs:1068), so existing config files that predate the three new fields still deserialize — the new ensure! checks in Config::validate() (crates/types/src/config/mod.rs:311-322) only bite if an operator explicitly sets one of the three fields to zero.
  • Ordering between two independent semaphores. The default HTTP admission budget (256) is far larger than the default chunk-lane budget (max_concurrent_chunk_ingress_tasks: 30, minus a control-plane carve-out), so under default config the backlog path is the expected steady state under any moderate burst, not an edge case — see Review-focus #1.

Review-focus map

These are attention pointers, not verified findings. Where a callout below looks serious, treat it as a lead for a dedicated /code-review pass, not a confirmed bug.

1Backlog-drain arm may queue exactly the kind of semaphore waiter the ADR says it avoids

The ADR states the design constraint plainly: fire-and-forget HTTP chunks "must not spawn acquire().await waiters on the shared chunk-lane semaphore: Tokio assigns released permits to that waiter queue before try_acquire, which would starve gossip," and concludes the chosen design "cannot ... queue Tokio waiters ahead of gossip try_acquire" (docs/adr/0001-http-chunk-ack-on-enqueue.md:23, 30). The implementation is exactly a conditional acquire_owned() branch on that same semaphore, active whenever the backlog is non-empty: 

res = Arc::clone(&self.inner.message_handler_semaphore).acquire_owned(), if drain_http_backlog => { ... }

(crates/actors/src/chunk_ingress_service.rs:444), competing in the same tokio::select! as self.msg_rx.recv() (468), which in turn feeds gossip/data-sync's try_acquire_owned() at 479. Tokio's semaphore (add_permits_locked in batch_semaphore.rs) hands a released permit directly to a queued waiter node before any surplus reaches the atomic counter that try_acquire reads, and poll_acquire enqueues that node on its very first poll if no permit is immediately available — confirmed by reading the vendored tokio-1.50.0 source, not just the ADR's own description.

Concrete failure scenario: two traffic shapes each break one of the ADR's two guarantees, depending on which branch tokio::select! happens to service first each loop iteration:

  • Continuous load (msg_rx almost always has something ready): the backlog-drain future is constructed and then dropped every single loop iteration before it can be woken by a real permit release, so it rarely wins the race to drain — the backlog can stall while fresh gossip/HTTP arrivals keep winning try_acquire_owned().
  • Bursty load with gaps (a quiet moment while the backlog is non-empty): the future genuinely suspends and registers as a waiter; the next permit release goes straight to it, bypassing the atomic counter — so a gossip chunk that arrives in that same gap gets a fast-fail Overloaded even though a permit was just freed. This is the specific outcome the ADR says cannot happen.

Neither direction is covered by a test that actually saturates message_handler_semaphore under concurrent HTTP + gossip traffic (see Review-focus #2).

2No test exercises the backlog-drain path under real semaphore contention

no_permit_action_backlogs_http_and_overloads_gossip (crates/actors/src/chunk_ingress_service.rs:846-870) only tests the pure classification function, not the live tokio::select! loop. The integration tests that touch saturation (preheader_rejects_when_cache_full, crates/chain-tests/src/multi_node/mempool_tests.rs:910) exercise the pre-header cache capacity, a different bottleneck from message_handler_semaphore. A regression in backlog fairness or drain latency under the exact contention pattern in #1 would not be caught by anything in this diff. Worth a dedicated concurrency/stress test before relying on the backlog for production HTTP load.

3Validation failures become invisible to the HTTP caller by design — verify nothing downstream still assumes synchronous rejection

This is the PR's stated intent, not a surprise, but it is a real behavior change worth a second look: a chunk with a bad merkle proof, wrong data hash, or one that fails the MDBX write now returns 200 and the failure is visible only in worker-side logs/metrics (crates/actors/src/chunk_ingress_service.rs:190-203). The ADR explicitly calls out that "integration helpers that treated HTTP 200 as 'chunk is stored' must poll" (docs/adr/0001-http-chunk-ack-on-enqueue.md:29) and the tests in this diff were updated accordingly, but any uploader outside this repository (SDKs, gateways, bridges) that still treats 200 from /v1/chunk as "accepted and valid" will silently stop detecting bad chunks. Worth confirming with whoever owns client-facing upload tooling before merge.

Open questions

  • Is there still a live, non-test caller of fire-and-forget IngestChunk(_, None, None) (no admission guard) anywhere, matching the "data_sync_service SM-write fallback" the doc comment at crates/actors/src/chunk_ingress_service.rs:101-102 describes? The lens could not find one, but no_permit_action would route such a message into the same unbounded backlog as HTTP-admitted chunks, with none of the HTTP semaphore's bound on how many can accumulate. If that call site is genuinely gone, the comment should be updated; if it still exists somewhere the lens missed, it changes the sizing story for the backlog.
  • Was the choice to make max_http_chunk_admission (default 256) roughly 8-9× larger than the default chunk-lane concurrency (max_concurrent_chunk_ingress_tasks: 30) deliberate, or should the two be tied together / validated against each other in Config::validate()? As shipped, the backlog is the expected steady state under any burst above ~26-30 concurrent chunks, not an edge case.
  • Is the 503 on WaitersSaturated / AdmissionTimeout intended to be retried by well-behaved clients on a fixed backoff, or should the response carry a Retry-After header given the 5s default timeout is itself close to typical client request timeouts?
