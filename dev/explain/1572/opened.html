Intent & approach

A peer-supplied PoA chunk with a length outside the bounds the validator implicitly assumed could crash the validating node. Two distinct panics were reachable from crates/actors/src/block_validation.rs:4608 (poa_is_valid): an oversized chunk fed crates/actors/src/block_validation.rs:4763 (xor_vec_u8_arrays_in_place, which indexes the shorter entropy buffer by the longer chunk's length) triggers an out-of-bounds index panic; an undersized chunk fed the old split_at(index) at the same site panicked when index > chunk.len(). Both panics happen inside a spawn_blocking task in the validation service (crates/actors/src/validation_service/block_validation_task.rs:594), which the PR description says surfaced as a node restart rather than a caught error.

The fix adds explicit length gates ahead of every unchecked use of chunk length, turning both panics into typed PreValidationError consensus rejections: PoAChunkTooLong (chunk longer than the packing/entropy limit) and PoAChunkTooShort (chunk shorter than the Merkle proof's expected byte span). Three new helpers carry the logic — block_validation.rs:4562 (reject_poa_chunk_longer_than), block_validation.rs:4577 (poa_chunk_within_configured_len), and block_validation.rs:4593 (poa_split_index) — and are called at three points: the cheap top-level hash check in prevalidate_block (block_validation.rs:1676), the entry of poa_is_valid before any Merkle work (block_validation.rs:4624), and immediately before the two panic-prone operations, the XOR (block_validation.rs:4762) and the trim split_at (block_validation.rs:4772).

Road not taken: the PR could have relied on the single upstream length check at poa_chunk_within_configured_len (comparing against config.chunk_size) and trusted that it implies both downstream operations are safe. It instead adds a second, independent guard at the entropy-XOR site keyed off entropy_chunk.len() rather than config.chunk_size. That choice is not redundant: compute_entropy_chunk (crates/c/src/capacity_single.rs:43) only fills (chunk_size / 32) * 32 bytes, so for a chunk_size not divisible by 32 the entropy buffer is strictly shorter than chunk_size and the upstream check alone would not have prevented the XOR panic. See Delta semantics.

Delta semantics

Error surface: two new PreValidationError variants, PoAChunkTooLong { chunk_size, limit, got } and PoAChunkTooShort { span, got } (block_validation.rs:181–190), both wired into the exhaustive classify() match as ErrorClass::Consensus (block_validation.rs:641–642) and the exhaustive metric_reason() match (block_validation.rs:723–724). Because both matches lack a wildcard arm by design (per the SAFETY comment at block_validation.rs:698), the compiler forced both call sites to be updated — this is why the classification is trustworthy rather than an oversight.

Failure-mode contract, before vs after: a peer that gossips a PoA chunk whose byte length is outside [proof_span, chunk_size] (or outside the entropy buffer's actual length when chunk_size % 32 != 0) previously crashed the validating thread; it now receives a typed, non-node-fault consensus rejection and the block is treated as invalid rather than the node treating itself as broken. is_node_fault() returns false for both variants (asserted directly in the new test at block_validation.rs:2857), so this is scored as an adversarial/malformed-input rejection, not a local-node health signal.

Ordering guarantee added: the length check in poa_is_valid's data-ledger branch runs before get_data_partition_assignment, validate_path (tx_path and data_path), and the owning-tx lookup (block_validation.rs:4624 precedes block_validation.rs:4631 onward). The new unit test poa_chunk_longer_than_chunk_size_is_too_long (crates/actors/tests/block_validation_tests.rs:155) constructs a PoaData against a default (empty) EpochSnapshot, so oversized-chunk rejection has to win the race against PartitionAssignmentMissing for the test to pass — this pins the ordering as a tested invariant, not an implementation accident.

u128 subtraction hardening (incidental to the stated fix): the old trim-index expression computed (max_byte_range - min_byte_range) as u64 directly on u128s; poa_split_index replaces the subtraction with saturating_sub (block_validation.rs:4594), which additionally removes a debug-build overflow-panic path if max_byte_range < min_byte_range were ever reached (the surrounding bounds checks at block_validation.rs:4745 make that state look unreachable today, but the new code no longer depends on that being true). The subsequent masking-and-try_from dance (block_validation.rs:4595) is functionally equivalent to the old truncating as cast on today's inputs; the comment at block_validation.rs:4591 frames it as preserving the exact same index, not changing behavior.

Review-focus map

  1. Low-severity / dead-code: block_validation.rs:4581 — usize::try_from(chunk_size) only fails when chunk_size > u32::MAX on a 32-bit target; on every 64-bit build (the project's actual targets) this branch, and its limit: 0 payload, is unreachable. Failure scenario: if this ever executed with limit: 0, the error message would misleadingly say the packing limit is 0 rather than reporting the real overflow — cosmetic today, worth a comment noting it is intentionally unreachable on supported targets rather than a forgotten case.
  2. Low-severity / consistency: block_validation.rs:4790 — the capacity-partition branch (no data_path/tx_path/ledger_id) still compares entropy_chunk != poa_chunk with plain Vec equality and never calls reject_poa_chunk_longer_than or checks a trim span. That's safe today (a length mismatch just makes the comparison false, yielding PoACapacityChunkMismatch, not a panic) — but this branch is exempt from the new PoAChunkTooLong/TooShort vocabulary purely because Vec::eq happens not to panic on length mismatch. A future edit to this branch that indexes into either buffer directly (mirroring the XOR-based branch) would reintroduce the same class of panic this PR just closed, without the new guard in scope to catch it.
  3. Low-severity / test asymmetry: crates/chain-tests/src/block_production/block_validation.rs:1591 — the new end-to-end test only shrinks the chunk by one byte, which fails via PoAChunkHashMismatch rather than PoAChunkTooShort (that variant is only reachable through poa_is_valid's deeper Merkle branch, not through prevalidate_block's shallow hash check). The test's own comment acknowledges this ("a short chunk must not be PoAChunkTooLong"), so the gap is at the boundary between the two validation phases rather than a missed assertion — but there is no chain-tests-level (as opposed to unit-level) coverage proving PoAChunkTooShort is reachable via the full node validation path, only via the lower-level unit test at block_validation.rs:8166.

These are attention pointers, not confirmed defects. If any of them looks worth escalating, run a dedicated code-review pass (/code-review) to verify before acting on it.

Open questions

  • Is 32-bit-target support for the validation crate still a live requirement? If not, the usize::try_from(chunk_size) fallback branch at block_validation.rs:4581 could be simplified or its unreachability documented explicitly.
  • Was it deliberate to leave the capacity-partition branch (block_validation.rs:4790) without its own explicit length guard, relying on Vec equality's safe-on-mismatch behavior, or should it get the same reject_poa_chunk_longer_than-style guard for symmetry and future-proofing?
  • Does the fix need a chain-tests-level (multi-node / gossip) regression test proving a peer that gossips an undersized PoA chunk is rejected end-to-end via PoAChunkTooShort, given the existing new test only reaches PoAChunkHashMismatch at that layer?
